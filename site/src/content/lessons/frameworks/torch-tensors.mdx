把一个两行三列的 NumPy 数组交给 PyTorch，六个数值可能保持不变，但修改是否传回原数组，取决于两者是否共享存储。转置通常改变 stride，索引操作还要求合适的类型。读张量时，要同时检查数值、轴、dtype、设备与存储关系。

先读 [F1 数组](/frameworks/numpy-arrays/) 与 [F2 批量计算](/frameworks/numpy-computation/)。本章沿用 `arange(6).reshape(2,3)`，再进入注意力常见的四维轴重排。所有运行核对使用 CPU、float64；整数索引用 int64。实际验证版本为 NumPy 2.5.2、PyTorch 2.14.0+cpu，使用的是 PyTorch 2.x 的基础 API。这里不假设已经安装 CUDA，也不把双精度当作大型模型训练的默认精度。

## 构造张量：共享输入还是独立保存

张量（tensor）在本章指 `torch.Tensor` 对象。它可以是零维标量、一维向量、二维矩阵或更多轴的数据。数学里的张量强调多轴关系，框架对象还负责内存与运算。若一个二维张量形状为 `(2,3)`，元素数是六；`ndim` 是轴数二，`numel()` 是元素数六，不能把二者混用。

最常见的三个入口有不同的所有权含义：

| 入口 | 本章普通 CPU NumPy 输入的行为 | 需要记住的边界 |
| --- | --- | --- |
| `torch.tensor(a)` | 复制数据，得到独立张量 | 从已有 Tensor 构造时也会复制并脱离原求导历史 |
| `torch.from_numpy(a)` | 对支持的 NumPy dtype 共享存储 | CPU 张量，不能通过它给共享存储随意改变大小 |
| `torch.as_tensor(a)` | 类型与设备允许时尽量共享 | 转换 dtype 或搬到其他设备时需要新的存储 |

“尽量共享”不是“任何输入都共享”。Python 列表本身没有可以直接视作张量的 NumPy 数值缓冲区。已有 Tensor 在 dtype、device 都匹配时，`as_tensor` 可以直接返回原对象，也保留其求导关系；需要转换时则遵循相应转换行为。若你就是需要一份与输入独立的快照，明确复制更容易审查。

```python
a = np.arange(6, dtype=np.float64).reshape(2, 3)
shared = torch.from_numpy(a)
copied = torch.tensor(a)
shared[0, 1] = 20
assert a[0, 1] == 20
assert copied[0, 1].item() == 1
```

这里不是 Python 变量赋值制造了神秘传播，而是 `a` 与 `shared` 指向同一块数据。改 `shared[0,1]` 就改了原缓冲区中的元素；`copied` 的缓冲区独立，所以保持 1。双向关系同样存在：改 NumPy 数组会改变共享的 Torch 值。给共享张量调用 `requires_grad_()` 也不会自动隔离 NumPy 的外部写入，因此需要求导的数据应谨慎管理外部可变别名。

共享要求 dtype、布局与设备可被接口支持。`from_numpy` 不是任意数组的转换器：负 stride 等布局可能不被支持，需要先复制成可接受布局；不可写 NumPy 数组也不能安全当作可写共享张量使用。这里选择普通可写、连续的 float64 数组，避开特殊存储形式。把零复制当成目标之前，先确定输入生命周期和谁被允许修改它。

## 类型与设备：数值相同仍可能不能一起运算

NumPy 默认浮点类型常是 float64，而 `torch.tensor([1.,2.])` 通常使用 PyTorch 默认浮点 dtype。为了让教学参考不依赖进程中的默认设置，本章在构造时显式写 `dtype=torch.float64`。`torch.long` 是 int64 的别名，常用于词表编号、类别目标与 `gather` 索引；把编号写成浮点数不会因为数值刚好是整数就满足索引接口。

设备（device）告诉我们存储和运算位于哪里。`x.device` 可以是 CPU，也可以是具体设备编号，例如 `cuda:0`。大多数普通张量运算要求参与数据处在兼容设备上；不能把 CPU 上的 mask 与 GPU 上的分数随意组合。某些标量接口有特殊规则，但不能由例外推导出所有设备混用都合法。

```python
x = torch.tensor([[1., 2., 3.]], dtype=torch.float64)
same = x.to(dtype=torch.float64)
changed = x.to(dtype=torch.float32)
assert same is x
assert changed.dtype == torch.float32
```

`to` 返回转换后的结果，不原地改变变量绑定。若类型与设备已经匹配，默认可返回原对象；因此 `y=x.to(...)` 不应被当作保证复制的写法。需要独立数据可以用 `clone()`，或者明确请求 `to(copy=True)`。转换到其他浮点类型通常仍是可微操作，转换到整数则不保留浮点求导需求；“复制”“设备搬运”和“停止梯度”是三个不同决定，下一章再区分。

`x.item()` 将单元素张量转成 Python 数值。它适合断言、日志和控制代码，但不能取多元素张量，而且结果不再是可求导的 Tensor。若数据在 GPU 上，取 Python 数值还可能需要等待设备完成。训练循环里为了打印而频繁读取标量，会改变执行边界；相关测量见 [G4](/gpu/measurement/)。本章 CPU 检查使用它只是为了明确比较一个数。

## Shape 与 stride：坐标怎样指向存储

形状（shape）说每条轴有多少位置，步长（stride）说轴坐标加一时跨过多少个存储元素。对二维视图，设起始存储元素偏移为 $p_0$，两条 stride 为 $s_0,s_1$，坐标 $(r,c)$ 对应的元素偏移是

<KeyEq label="张量坐标到存储元素">
$$
p=p_0+rs_0+cs_1.
$$
</KeyEq>

Torch 的 `stride()` 以元素为单位，NumPy 的 `strides` 通常以字节为单位，迁移时要先核对单位。若张量为 float64，最终字节偏移再乘八。下文交互使用起点为零的简单视图；真实切片还可能有非零 `storage_offset()`。

连续的 `arange(6).reshape(2,3)` 按行存储为 `[0,1,2,3,4,5]`，stride 是 `(3,1)`。行坐标加一跳过三个元素，列坐标加一跳过一个元素。因此 `(1,2)` 指向偏移 $1\cdot3+2=5$。转置得到形状 `(3,2)`、stride `(1,3)`；现在 `(2,1)` 也指向 $2\cdot1+1\cdot3=5$，数据本身没有重新排序。

上方每格显示当前逻辑坐标读到的值，下方是固定的底层存储。勾选转置后，格子从两行三列变成三行两列，箭头仍指向相同缓冲区。把逻辑展开位置调到 1，原布局读偏移 1，转置布局读偏移 3。这就是“按当前逻辑顺序展平”和“底层物理存储顺序”不同的具体证据。

连续（contiguous）描述形状与 stride 满足某种连续内存格式。这里讨论默认的行主序连续格式，不涉及 channels-last 等专门格式。转置后的六个元素仍然在一个存储区域里，但按当前轴的行主序遍历需要跳跃，因此 `is_contiguous()` 为假。不要把“存储是一整块”与“当前逻辑视图连续”混成同一句话。

## View 与 reshape：重排形状的约束不同

`view` 在已有存储上改变形状解释，不能为满足请求而复制元素。因此它要求原有 stride 与目标形状兼容。连续的 `(2,3)` 可以 `view(6)`；转置后的 `(3,2)` 按逻辑顺序应展平为 `[0,3,1,4,2,5]`，这些地址无法用一条固定元素步长表达，直接 `view(6)` 会报错。

```python
x = torch.arange(6, dtype=torch.float64).reshape(2, 3)
y = x.transpose(0, 1)
z = y.reshape(6)
assert z.tolist() == [0., 3., 1., 4., 2., 5.]
```

`reshape` 优先在可行时返回视图，否则创建满足逻辑顺序的新存储。它保证形状和元素解释，不能被当作存储共享的承诺。在这个特定转置展平例子里，需要复制。后续写 `z` 不会修改 `x`；换一个兼容输入，`reshape` 却可能共享。程序若依赖独立性，额外明确 `clone()`；若依赖共享，使用能验证契约的视图并检查实际布局。

不能简单说“非连续就不能 view”。某些非连续切片仍能在兼容的轴组合上建立视图，判断条件涉及相邻维度的 stride 关系；本章反例证明的是这个具体转置无法展平。遇到复杂布局，先写出目标逻辑遍历需要的地址，而不是把 `view` 报错当成随机限制。

`contiguous()` 返回满足要求的连续张量，已经连续时可返回自身，需要时才复制。常见的 `y.contiguous().view(6)` 把两个意图分开：先保证布局，再建立形状视图。但为了所有 `view` 都不报错而到处加 `contiguous()`，可能引入大量搬运。应先确定下一算子的布局契约，只有需要时才整理。

`reshape` 也不能代替转置。将 `(2,3)` 直接 `reshape(3,2)`，按原逻辑顺序得到 `[[0,1],[2,3],[4,5]]`；转置得到 `[[0,3],[1,4],[2,5]]`。两者形状相同，轴意义和数值位置不同。这类错误常不会抛异常，所以必须用带坐标的具体元素核对。

### 切片的起点也参与地址计算

从六个数中取 `x[:,1:]`，形状变成两行两列，原 stride 仍是 `(3,1)`，起始存储偏移变成 1。它的逻辑值是 `[[1,2],[4,5]]`，第二行并不是紧跟第一行的第二个数，而是仍要跨原来的三个元素。这里的有效数据只有四个数，底层存储仍可保存原来的六个数，因此 `numel()` 不能当作该对象实际保留存储大小的通用解释。

对这份切片来说，坐标 `(1,1)` 指向 $1+1\cdot3+1=5$。省略起点会误读为 4，擅自把行 stride 改成新的列数二又会误读为 4。形状、步长和起点必须一起描述一个视图。当读取或写入自己实现的底层算子时，仅传 shape 而忽略 stride，正是把这种逻辑切片错误当成连续数组的来源。

“把数据切小”也不必然释放原大存储。如果缓存里长期保存一个很小的视图，它可能使整个源存储继续存活。需要独立保留小结果时，可以根据用途复制；如果只是短期读取，视图则省去搬运。这不是推荐所有切片都 clone，而是提醒存储生命周期由共享关系决定，不能从输出形状猜内存占用。

## 四维轴重排：时间与头怎样交换

注意力中常出现 `(B,T,H,D)`，这里 B 是批大小，T 是序列长度，代码 H 表示头数，D 对应每头通道数 $d_h$。从每个位置携带多个头的布局，换成每个头携带完整时间序列的布局，需要把时间与头两条轴交换。

```python
x = torch.arange(24, dtype=torch.float64).reshape(1, 3, 2, 4)
y = x.permute(0, 2, 1, 3)
assert y.shape == (1, 2, 3, 4)
assert y[0, 1, 2, 3] == x[0, 2, 1, 3] == 23
```

`permute` 的参数描述输出各轴来自输入哪条轴。`(0,2,1,3)` 的输出第一轴来自输入 0，第二轴来自输入 2，第三轴来自输入 1，最后一轴来自输入 3。每条原轴必须出现一次。`transpose(i,j)` 只交换指定两条轴，其他轴保留；在这个例子中，`transpose(1,2)` 与上述 `permute` 得到相同轴顺序。

<Figure src="frameworks/torch-axis-layout.svg" alt="同一元素23从批时间头通道坐标变为批头时间通道坐标，stride随轴交换">两边数值 23 没有变化，变化的是时间与头的位置；下方 stride 对应轴解释，箭头表示视图重排，不表示复制数据。</Figure>

例如原 stride 是 `(24,8,4,1)`，交换后为 `(24,4,8,1)`。头坐标加一只跨四个元素，时间坐标加一跨八个元素。这个图只画轴关系，不显示实际 GPU cache 或线程分配。张量轴与 GPU block 轴属于不同层次，后续 kernel 必须自己决定二者怎样映射。

多头输出需要恢复 `(B,T,H,D)` 后，才能把相邻 H、D 合并成隐藏维度。先交换回来，再 `reshape(B,T,H*D)`，会按预期把同一时间位置的各头通道拼在一起；若直接对 `(B,H,T,D)` reshape 成 `(B,T,H*D)`，元素数虽匹配，却把头与时间顺序混在一起。写轴重排最有效的检查是固定一个 `(b,t,h,d)`，一路跟踪它的值，而不只断言最终 shape。

## 新增轴与广播：复制多少数据由接口决定

`unsqueeze(dim)` 新增长度一的轴，不改变元素数。例如 `(2,3)` 在维度 0 扩成 `(1,2,3)`，在末尾扩成 `(2,3,1)`。这是表达广播所需的轴身份，不是增加一份数据。`squeeze(dim)` 只在指定轴长度为一时移除它；无参数的 `squeeze()` 会移除所有长度一的轴，可能把 B=1 的批轴意外去掉。

若模型接口要求一直保留 `(B,T,D)`，写 `squeeze(1)` 比无条件 `squeeze()` 更能说明你只想删除哪条轴。零维张量也仍是 Tensor，不能把标量张量与 Python 标量自动等同。批大小改变后才出现的 shape 错误，常来源于过于宽泛的 squeeze。

`expand` 把长度一的轴广播成更大尺寸，采用零 stride 让多个逻辑位置引用同一个元素。`repeat` 按指定倍数实际复制数据。对 `[[1,2,3]]`，两者都能得到看起来相同的两行，但存储含义不同：

```python
base = torch.tensor([[1., 2., 3.]], dtype=torch.float64)
shared_rows = base.expand(2, 3)
copied_rows = base.repeat(2, 1)
assert shared_rows.stride() == (0, 1)
base[0, 0] = 9
assert shared_rows[1, 0] == 9
assert copied_rows[1, 0] == 1
```

`expand` 不能把任意长度二的轴扩成三，因为这不是可广播的轴。扩出来的多个位置会重叠，不能把它当作独立可写矩阵；批量原地操作可能报错，单个位置的写入也会影响其他别名。若需要独立修改，先 `clone()`。`repeat` 分配更多存储，但数值复制不等于切断梯度：源值对多个复制位置有贡献时，反向仍会把这些贡献相加，见 [F4](/frameworks/autograd/)。

## 拼接与索引：轴身份不能由数值猜测

`cat` 沿一条已有轴拼接，其他轴尺寸必须匹配。两个 `(2,3)` 沿 0 拼接变 `(4,3)`，沿 1 拼接变 `(2,6)`。`stack` 新增轴，输入 shape 必须一致；两个 `(2,3)` 在轴 0 堆叠变 `(2,2,3)`。前者延长一条轴，后者记录“来自哪一份输入”的新身份，不能互相替代。

`gather` 用逐位置的整数索引选择元素。输入与索引具有相同轴数，不会像普通算术那样自动广播；输出 shape 与 index 相同。对不是 gather 轴的维度，index 尺寸不能超过输入对应尺寸。索引必须在目标轴范围内，常用 dtype 是 `torch.long`。

```python
scores = torch.tensor([[10.,20.,30.], [40.,50.,60.]], dtype=torch.float64)
index = torch.tensor([[2,0], [1,1]], dtype=torch.long)
selected = scores.gather(1, index)
assert selected.tolist() == [[30.,10.], [50.,50.]]
```

这里 `dim=1` 表示每个输出沿本行选择列号。第二行两次选择列 1，所以得到两个 50；它不是“把索引1的那一整行取两次”。类别概率按目标类别提取、每位置选择候选值时，这种逐行索引很常见。先在两行三列上手算，才能正确迁移到 `(B,T,C)`。

`masked_fill` 用 bool mask 将 True 的位置填成给定值，mask 必须能广播到输入 shape。它默认返回结果，带下划线的 `masked_fill_` 才是原地版本。屏蔽语义别反过来：True 表示要填充，不是要保留。形状 `(1,3)` 的 mask 可以作用到 `(2,3)`，同一列规则广播给两行。

索引与掩码还要区分“取出一个更小结果”和“保持原形状但改变值”。布尔索引通常把选中的元素收集成新的结果，轴可能被压缩；masked_fill 则保留输入所有位置，只在指定位置写替代值。若后续运算要求固定的 `(B,T,C)`，用布尔索引删除位置可能破坏轴意义，不能因为两个操作都接受 bool 就认为用途相同。

同样，带重复索引的读取是有定义的，但重复位置的写入需要额外明确如何合并。gather 只负责读取，它不会把两次读取自动变成两个独立参数。下一章反向时，重复读取同一源值所产生的梯度贡献要汇合相加。如果你需要将多个值加回索引位置，应查散射加法等专门接口，而不是普通索引赋值后期待它完成求和。

给未归一化分数填负无穷，随后 softmax，可让被屏蔽位置概率为零；但整行全被屏蔽时普通 softmax 会遇到未定义的情况。mask 能广播不代表算法定义完整，要另行决定空行策略，参见 [G3](/gpu/kernel-design/)。若使用零填充，softmax 仍可能给它非零概率，因此“把值变成零”与“排除概率候选”不是同一操作。

## 核对与回查：每次接口转换检查什么

### 排查顺序：从一个元素到完整算子

假设模型某个张量形状已经是预期的 `(1,2,3,4)`，但数值对不上。先固定一个可手算的位置，例如 `(0,1,2,3)`，沿每次轴操作倒推它来自哪个原坐标。若原本应来自 `(0,2,1,3)`，却读到另一个位置，问题属于轴重排；此时改 dtype 或加 contiguous 都不能修好数学关系。

若坐标映射正确，再检查输入是否被另一别名修改、是否发生不期望的整数或低精度转换、mask 的 True 是否反向、gather 索引是否沿正确的轴。在确认数值与布局后，再讨论搬运次数与设备性能。这个顺序让错误定位依赖可检查的事实，而不是不断试不同 reshape 直到报错消失。

输出尺寸很小的手算例子不是玩具限制，而是完整模型契约的缩小版本。测试中把批大小设为一可以发现宽泛 squeeze，设置非连续输入可以发现连续布局假设，选择重复 gather 索引可以发现梯度汇合需求。每个边界都对应真实模型中可能出现的输入，检查应围绕这些具体风险安排。

最后，把输入支持范围写在函数旁边。如果只支持连续行主序，就在入口明确检查并给出可理解的错误；如果要支持视图，就传递并使用真实 stride。两种接口都可以合理，错误在于声明支持任意形状视图，内部却偷偷按连续数组寻址。框架提供便利转换，但不能替实现者补写缺失的输入契约。

本文的存储讨论仅针对普通稠密张量。稀疏、量化、特殊设备与自定义张量子类可能具有其他约束；迁移本章例子时应先确认自己使用的对象类型，再把 shape 与 stride 模型应用到对应接口。

| 想做的事 | 首先核对 | 常用 API |
| --- | --- | --- |
| 保存输入快照 | 是否需要独立存储与求导关系 | `tensor`、`clone` |
| 共享 NumPy 数据 | dtype、写入权限、存储生命周期 | `from_numpy`、`as_tensor` |
| 改形状 | 元素数与 stride 是否兼容 | `view`、`reshape` |
| 换轴意义 | 每个输出轴来自哪条输入轴 | `permute`、`transpose` |
| 扩展长度一的轴 | 是否要独立修改 | `expand`、`repeat` |
| 逐行选择 | 索引轴、shape、long 与范围 | `gather` |
| 排除位置 | True 的意义、广播与空行策略 | `masked_fill` |

## 常见误区

- 打印数值相同不证明存储独立，复制与共享要从构造和视图接口判断。
- `reshape` 保证逻辑形状，不保证一定共享或一定复制；`contiguous` 也可能返回自身。
- 同样的 shape 不代表轴意义相同，转置与 reshape 必须用具体元素对照。
- 零 stride 的 expand 视图不适合按独立元素批量原地修改。
- 索引是整数身份，浮点 dtype 不能代替 `long`；mask 是布尔条件。
- 布局整理不会自动停止梯度；停止求导留到 F4 明确决定。

## 练习与核对

<details>
<summary>from_numpy 得到的张量改一个元素，torch.tensor 构造的副本会跟着变吗？</summary>

不会。前者共享 NumPy 缓冲区，后者复制了构造时的数据。若两者曾显示相同数字，那只是复制完成时的状态，不是共享承诺。
</details>

<details>
<summary>连续的 2×3 张量转置后，坐标 (1,1) 指向哪个偏移？reshape(6) 的顺序是什么？</summary>

转置 stride 为 `(1,3)`，偏移是 $1+3=4$。按三行两列展开，偏移依次为 0、3、1、4、2、5；为得到该逻辑顺序的连续一维结果，这个例子需要复制。
</details>

<details>
<summary>将 B,H,T,D 直接 reshape 为 B,T,H·D，为什么形状正确仍可能算错？</summary>

reshape 保留当前逻辑遍历顺序，不交换 H 与 T 的意义。先把轴恢复为 B,T,H,D，再合并邻接 H、D，才能把同一时间位置的各头通道放在一起。跟踪一个带编号的元素即可发现错位。
</details>

<details>
<summary>expand 两行之后修改源数组，会不会改变两行？repeat 呢？</summary>

expand 的行 stride 为零，两行指向同一源值，所以都会改变。repeat 创建独立复制的数据，构造后改源值不会传播；但 repeat 仍可保留与源值的可微关系。
</details>

<details>
<summary>gather(1, [[2,0],[1,1]]) 的输出形状是什么，第二行为什么重复？</summary>

输出形状与 index 相同，为 `(2,2)`。第二行的两个输出各读取输入第二行的列 1，允许重复索引。它没有新增轴，也没有将整行重复拼接。
</details>

数据与轴关系清楚后，进入 [F4 自动微分](/frameworks/autograd/)，区分存储共享、计算历史与梯度保存。
