在 [M7](/math/training/) 中，网络输入已经是实数；这里从字符串 `猫 sat` 出发，一直走到可训练的向量序列。先修只用到 [M3 的矩阵索引](/math/linear-algebra/) 和 M7 的参数更新。我们会让教学 tokenizer 在四份相同的 `猫 sat` 上学习两次合并，用它编码原句，再追踪同一组 ID 如何选取 embedding 行。生产 tokenizer 的额外规则放在这条链完成之后。

## 起点：同一句话能怎样切分

`猫 sat` 可以按五个 Unicode 码点切为 `猫`、空格、`s`、`a`、`t`，也可以把 `sat` 当成一段；这两种切法都不是模型天然拥有的。token 是 tokenizer 输出的离散单位，可能对应一个词、词的一部分、空白，甚至单个字节。它的边界由具体 tokenizer 的规则决定。把 token 一律理解为“字”或“词”，会误读模型长度限制与每 token 统计量。

本章采用**字节级 BPE**：先把 Unicode 字符串编码成 UTF-8 字节，再合并频繁相邻的片段。`猫` 是一个码点 U+732B，却占三个 UTF-8 字节 `E7 8C AB`；` sat` 是四个 ASCII 字节 `20 73 61 74`。因此初始序列是：

| 输入片段 | 猫 | 空格 | s | a | t |
| --- | --- | --- | --- | --- | --- |
| UTF-8 十六进制 | `E7 8C AB` | `20` | `73` | `61` | `74` |
| 初始十进制 ID | `231,140,171` | `32` | `115` | `97` | `116` |

此时 ID 0 到 255 各代表一个字节，全部保留在词表中；中文的三个字节不要求分别能显示成字符。只要输入能按 UTF-8 编码，基础字节就能覆盖它，无须未知字符 ID。按 Unicode 码点或用户眼中的“字符”切分会有不同边界，例如组合重音可以由多个码点形成一个可见字符；**字节覆盖**也不能推广成所有 tokenizer 都没有未知项。

## 两次 BPE 合并：怎样从字节得到 token

BPE 的训练把相邻 token 对按频次计数，选中一对后给连接后的字节串一个新 ID，再重新计数。训练语料暂取四份独立的 `猫 sat`，不跨文档边界合并。第一轮每个相邻对都出现四次；教学实现用 ID 对的字典序打破并列，因此选 `(32,115)`，也就是空格与 `s`，合为 ID 256：

```text
初始  [231, 140, 171, 32, 115, 97, 116]
一次  [231, 140, 171, 256, 97, 116]   256 = b" s"
二次  [231, 140, 171, 256, 257]        257 = b"at"
```

第二轮剩余各相邻对仍各出现四次，最小的 ID 对是 `(97,116)`，所以把 `at` 合为 257。词表此时有 258 项：256 个基础字节加两个合并片段。切分成为五个 token，原始七个字节没有丢失。这里语料故意极小，并列选择是教学代码的**确定性约定**；生产语料中的合并由其数据与实现决定，不应从这两条规则推断实际模型的中文切法。

## `encode` 与 `decode`：规则如何变成稳定契约

训练得到的合并顺序固定后，`encode("猫 sat")` 先取得七个字节 ID，再依次应用 `(32,115)→256`、`(97,116)→257`，结果是 `[231,140,171,256,257]`。面对新句子也应用**同一套规则**，不会重新统计新句的高频对。词表中有某片段，并不允许随意改为最长匹配：合并优先级和编码算法共同决定最终切分。

`decode` 查出每个 ID 对应的字节串，先拼接为 `E7 8C AB 20 73 61 74`，再对**完整字节串**做 UTF-8 解码，得到 `猫 sat`。单独解码 ID 231 对应的 `E7` 会失败，因为它只是中文字符的第一个字节。对本章未做规范化的普通文本，`decode(encode(text)) == text`；对任意乱序 ID 或截断的字节序列，这个等式没有保证。

这一步说明 ID 是地址，不是连续数值特征。ID 257 比 256 大 1，不表示 `at` 比 ` s` 更接近任何含义。固定 tokenizer 的完整状态后才训练模型；只改 ID 对应片段而保留模型权重，输入和输出类别都会错位。

## 特殊 token：控制标记不能从普通文本里猜

语言模型可能需要表示文档开始与结束的特殊 token。对当前词表声明 `<bos>` 和 `<eos>` 后，它们分别取得 ID 258、259，和普通字节片段分开。训练样本可以由程序明确组装为 `[258,231,140,171,256,257,259]`；普通句子 `猫 sat` 的 `encode` 本身仍只返回五个正文 ID。下一章会用开始 ID 预测第一个正文 token，并把结束 ID 作为最后目标。

特殊 token 的**拼写**与**控制含义**也必须分开：用户输入字面字符串 `<eos>`，普通 `encode` 将它当作普通文本的字节来编码；只有调用 `encode(text, allowed_special=True)` 才把它识别为控制 ID。`decode` 可以显示两者同样的拼写，但不能从显示文本反推当初是哪种 ID 序列。模型是否自动加标记、对话模板如何插入标记，都须看对应模型约定。

两个合并项使基础词表大小为 258，再加两个特殊 token 才是 $n_{\mathrm{vocab}}=260$。先固定合并规则与特殊 ID，再创建模型；额外学一次合并会移动特殊 ID。脚本的 `save` 把算法类型、合并顺序和特殊项写入 JSON，`load` 恢复并检查非法引用。训练和推理应读取同一份状态，不能只凭词表大小重新构造映射。

## embedding：ID 怎样选到可训练向量

embedding 是按 ID 查表的可训练矩阵。当前完整词表有 260 项；若隐藏维度暂取 $d=2$，矩阵 $E\in\mathbb R^{260\times2}$ 有 260 行，每行两个实数。对正文序列 `[231,140,171,256,257]`，输出的形状是 $(5,2)$：第一个位置取 $E_{231,:}$，第四个位置取 $E_{256,:}$。例如设 $E_{256,:}=(0.2,-0.1)$，该位置的输出就是 $(0.2,-0.1)$；数字 256 本身不会乘入向量。加上 BOS/EOS 后则是七个位置，形状 $(7,2)$。

对 batch 中 $B$ 条等长序列，每条长度 $T$，ID 数组形状是 $(B,T)$，查表后是 $(B,T,d)$。令 $e_u$ 为仅第 $u$ 项为 1 的 one-hot 列向量，则单个输出列向量也可写成 $x=E^\top e_u$。这只是解释索引的等价式；实现直接取行，无需真的建 260 维 one-hot 向量。

现在把 `猫 sat` 放入同一个 batch 两次。两条样本第四个位置都是 ID 256，都读取**同一参数行** $E_{256,:}$。若损失对两个输出位置传回的梯度分别是 $g_1=(1,2)$ 与 $g_2=(3,-1)$，链式法则在共享行汇合，得到

$$
\frac{\partial L}{\partial E_{256,:}}=g_1+g_2=(4,1).
$$

这是 [M6](/math/backprop/) 的共享节点梯度相加。ID 是离散地址，不对 ID 求导；未被查到的行对**这一次输入查表**没有梯度贡献。若 $L$ 是两个样本的平均损失，平均因子已经包含在上游 $g_1,g_2$ 中，不应在相加后再除以 2。随机初始化的 embedding 也没有天然词义，只有经过后续预测目标训练，行向量才可能学到有用表示。

这样，开篇问题已经闭合：`猫 sat` → 七个 UTF-8 字节 → 五个普通 token ID → 五行可训练向量。若附加控制 ID，则序列从五个位置变成七个位置。下一章在这些位置上定义“预测哪一个 ID”。

## 边界：教学 BPE 与生产 tokenizer 差在哪里

本章直接对整段 UTF-8 字节做 BPE。生产 tokenizer 可以先**规范化**文本，把多种字符写法变成同一种；这种处理可能使 `decode(encode(text))` 不再与输入逐字节相同。它也可以先按正则规则**预分词**，再仅在块内合并。对 `猫 sat`，若把中文片段与带前导空格的英文片段划成两块，当前两条合并仍在英文块内，结果不变；若语料中某个高频对跨越块边界，整段 BPE 可以合并它，预分词版本则不会。实际块边界应以具体 tokenizer 文件为准。

GPT-2 的字节级 tokenizer 使用正则预分词；配套脚本用简化的 ASCII 规则比较 `a b`，说明跨边界合并为何会改变。SentencePiece 则把空格表示为可见的 `▁`，支持 BPE 和另一种 Unigram 训练算法。Unigram 为候选片段赋概率，在编码时寻找整体得分最好的切分，并不使用本章的逐轮合并优先级。它是否支持未知字符的字节回退还要看配置。这些实现都可以把**同一字符串**切成不同 token；训练与推理必须使用对应模型的同一 tokenizer。

词表与模型也是一份契约：只重排 ID 会改变输入 embedding 的行与输出类别的含义。embedding 参数量为 $n_{\mathrm{vocab}}d$；词表变大通常有机会缩短序列，也会扩大输入表和输出 LM head。具体计算成本取决于模型结构，不能只看 token 数；[S1](/systems/ledger/) 会分别记账。

## 常见误区

- 把 token 数当字符数。英文、中文、空白和不同分词规则都可能使这个比例改变。
- 把 ID 大小当连续数值特征。embedding 选行，不以 ID 的数值做乘法。
- 一边训练网络一边随意改词表。既有参数行和输出类别都因此改义。
- 对单个字节 token 强制解码并据此判断分词器损坏。需要检查完整字节序列。
- 把教学字节 BPE 当成生产 tokenizer 的全部处理流程。规范化、预分词和特殊标记都属于契约。

## 练习与核对

<details>
<summary>不重新训练 tokenizer，仅把待编码句子改成 `猫 sat!`，`encode` 的结果是什么？</summary>

这里**不重新 fit**，只拿已固定的 `(32,115)→256`、`(97,116)→257` 编码新句。新增的 `!` 是字节 33，所以得到 `[231,140,171,256,257,33]`，`decode` 仍还原 `猫 sat!`。如果真的重新训练，频次与并列规则也要重新计算，不能沿用这个答案。

</details>

<details>
<summary>同一 batch 的两条 `猫 sat` 中，ID 257 的上游梯度为 `(1,3)` 和 `(-2,4)`。该行 embedding 梯度是多少？</summary>

ID 257 对应 `at`，两处使用同一行，梯度相加为 $(-1,7)$。如果上游梯度来自 batch 平均损失，平均因子已经在给出的两个向量里。

</details>

<details>
<summary>训练后把 ID 256 与 257 对调，只交换 embedding 两行够吗？</summary>

不够。输入行要对调，输出 LM head 的对应类别也要对调，输出偏置若存在也要同步；tokenizer 中两个 ID 对应的片段与合并规则必须同步改动。任何一处遗漏都会让 ` s` 与 `at` 的含义错位。更稳妥的是保持训练时的 tokenizer 不变。

</details>
