`Decoder` 能算 logits，`sequence_loss` 能算下一 token 损失，但这还不是一次可复现的训练。我们要完成一项可以独立核对的实验：同一批文档训练 30 次参数更新，中断于第 18 次后恢复，检查剩下 12 次是否与连续运行完全相同。阅读前建议掌握 [T1 样本构造](/training/data/)、[T2 AdamW 与梯度裁剪](/training/optimization/) 和 [P4 Decoder](/principles/decoder/)；生成调用见 [P9](/principles/generation/)。

## 输入与目标：一次更新恰好监督 11 个位置

这里的 tokenizer 是固定映射 `a=0, b=1, c=2, EOS=3`。三篇训练文档各有 11 个字符，末尾添加 EOS；第一篇的完整 ID 是 `[0,1,2,0,1,2,0,1,2,0,1,3]`，另外两篇分别从 `b`、`c` 开始，同样遵循 `a→b→c→a`。两篇验证文档各有 9 个字符和 EOS，与训练文档没有逐字相同，但共享刻意设计的循环规则。这个划分只能检验新长度上的同规则预测，不能代表开放领域泛化。

每步选**一整篇**训练文档：`inputs = document[:, :-1]`，`targets = document[:, 1:]`。第一篇的输入 `[0,1,2,0,1,2,0,1,2,0,1]` 和目标 `[1,2,0,1,2,0,1,2,0,1,3]` 各有 11 个位置。第 0 行从 `a` 预测 `b`，末行在完整前缀后预测 EOS；没有 BOS，所以不监督文档首字符。每篇独立送入模型，不存在跨文档注意力或 padding。训练 30 步共计算 **330 个有效目标**；验证两篇共 **18 个有效目标**。这里的目标数是被计入损失的位置数，不是去重后的文本 token 种类数。

`Decoder` 有两层、隐藏宽 16、两个查询头（每头宽 8）、前馈宽 32 和最大输入长度 12；它使用学习式位置 embedding、pre-LayerNorm 与 GELU。教学配置来自 [P4](/principles/decoder/)，不是某个公开模型的缩小版。PyTorch 固定种子 29、CPU float64、AdamW 学习率 0.01、权重衰减 0.01、全局梯度裁剪阈值 1。固定这些条件是为了能比对两个轨迹；float64 不是生产训练建议。

## 前向与损失：每行预测下一个 ID

第一篇输入张量形状 $(B,T)=(1,11)$，模型给出 $(1,11,4)$ 的 logits，其中最后一轴是四个候选 ID 的原始分数。因果 mask 保证第 $t$ 行只能读到第 $t$ 个输入及之前的内容。令 $y_t$ 是该行的目标，损失是

<KeyEq label="一篇文档的下一 token 损失">
$$
L=\frac1{11}\sum_{t=0}^{10}-\log\frac{e^{z_{t,y_t}}}{\sum_{v=0}^{3}e^{z_{t,v}}}.
$$
</KeyEq>

`sequence_loss` 用稳定的交叉熵计算同一式子。第 11 个目标 EOS 也占分母中的一个位置；不能把 11 个位置的损失相加后当作平均损失，也不能拿输入本身作标签。检查第 0 行的输入/目标 `0→1` 和末行的 `1→3`，就能发现最常见的移位错误。若以后用 padding，损失 mask 还必须把无效行排出求和及分母；本例没有这一步。

## 第一步更新：损失怎样改变参数

第一次更新使用上面的 11 个目标。先调用 `model.train()` 设置训练模式，再清空上一步梯度、前向、计算平均损失、反向、裁剪和更新。`backward()` 产生梯度；只有 `optimizer.step()` 改变参数。对第 $k$ 步可记成 $\theta_{k+1}=\operatorname{AdamW}(\theta_k,\nabla_\theta L_k,s_k)$，其中 $s_k$ 是动量等优化器历史，计算细节见 [T2](/training/optimization/)。

```python
optimizer.zero_grad(set_to_none=True)
logits = model(inputs)
loss = sequence_loss(logits, targets)
loss.backward()
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
optimizer.step()
```

`train_steps` 每步抽一篇完整文档，前 3 步按编号取样；走完一轮后用 PyTorch RNG 打乱下一轮的文档顺序。30 步仍各有 11 个目标，但后续顺序随机。裁剪在 `backward()` 之后、`step()` 之前，对**所有参数的整体梯度范数**执行。把每个微批各自裁剪再相加，与 [T2](/training/optimization/) 的完整有效目标平均及裁剪次序不同。

主实验外另有一次固定批探针：以种子 31 新建同配置模型，只反复训练第一篇 60 步，NLL 从 1.387822 降到 0.002195。它检查移位、梯度和更新链能否拟合这 11 个目标；探针不参加主实验的验证或 checkpoint 选择，更不能当作泛化结果。

## 验证：固定 18 个目标的观察

在任何更新之前，先用同一两篇验证文档测 NLL；第 30 步后再测一次。验证函数用 `model.eval()` 设评估模式，用 `torch.no_grad()` 关闭梯度记录。前者会改变 dropout 等模块行为，后者不会自动改变模块模式；本例没有 dropout，但两个动作仍各司其职。

验证两篇等长文档直接合成形状 $(2,9)$ 的输入与目标；`sequence_loss` 将两篇的 18 行共同平均。若文档长度不同，须对各批损失乘以各自有效目标数，再除以总数；简单平均批均值会改变指标。这个归约在 [T4](/training/evaluation/) 继续展开。

验证函数不执行 `backward()` 或 `step()`；继续训练时 `train_steps` 会重新调用 `train()`。脚本本次运行从 1.354763 降到 0.707979，只断言最终值低于初始值。这里报告的是预定第 30 步，不是看完验证曲线后挑最优的一步；一个种子的一次下降尚不能证明对自然文本有效。

## Checkpoint：保存的是下一步需要的全部历史

模型参数只描述当前函数。AdamW 的一阶矩、二阶原始矩和步计数描述优化历史；PyTorch 随机状态决定下一轮文档顺序，数据游标决定本轮下一篇。恢复参数却丢失其中任一项，都可能得到不同训练轨迹。

<Figure src="training/checkpoint.svg" alt="更新结束时保存参数、优化器、随机状态和游标，恢复后核对下一步">四类状态在同一个更新边界保存，恢复时共同决定下一次训练事件。参数相同只是其中一项条件。</Figure>

脚本保存模型配置、tokenizer 映射、模型与优化器 `state_dict`、已完成步数、当前顺序与游标、PyTorch RNG 状态。打乱文档顺序只使用 PyTorch RNG；主实验不使用 Python、NumPy、CUDA 或数据加载 worker 的随机源。真实训练若用到了这些来源，就要保存相应状态与采样协议。

快照选择在完整 `optimizer.step()` 后、下一批抽样前。这样不需要额外保存未完成的梯度累积。如果允许在某个微批之间中断，就还要保存当前梯度、累积目标数和微批进度，复杂度明显增加。先选择清楚的更新边界，可以让恢复协议更简单。

`state_dict()` 中张量可能仍共享当前存储。若在内存保存字典后继续训练，旧快照可能一起改变，因此脚本用深拷贝；再写入内存字节流，模拟明确的序列化边界。真实磁盘文件的写入和原子替换在后面的文本实验完成。

加载时使用 `weights_only=True`，当前 payload 只包含张量和基本 Python 容器。不要把任意来源的 checkpoint 当可信代码执行；包含自定义对象的其他格式还需另行处理信任边界。

## 恢复检验：连续和中断怎样形成同一个实验

先训练 18 步（198 个目标）并保存快照，继续训练 12 步（132 个目标），记录每一步损失与最终参数。再创建新模型和新优化器，加载快照，并在模型初始化消耗随机数之后恢复 PyTorch RNG。随后从保存顺序和游标继续执行 12 步，逐项比较损失、游标、顺序和所有参数。两条路径总共都经历 330 个训练目标。

恢复顺序很重要：如果先恢复 RNG，再随机初始化新模型，初始化就消耗了本应属于后续抽样的随机数。模型模式不包含在普通权重字典中，恢复后也要明确设置训练或评估模式。学习率日程若存在，则在对应 optimizer 状态之后恢复，并核对下一步学习率。

脚本设置 CPU 单线程、无 dropout、float64，检查恢复后损失和参数完全相等。这个严格相等只证明指定环境下的恢复协议。GPU 内核、分布式规约或版本变化可能带来数值差异；跨环境恢复要另定容差和数据协议。

只比较加载后立刻的模型输出还不够，因为丢失 AdamW 状态时，加载后的前向仍能相同。至少比较一次后续更新；本章比较十二步，包含重新打乱文档顺序的时刻，确保随机和游标都真正参与核对。

为了直接看见每类遗漏，这里另建一个**单参数恢复探针**，不把它当作上面 30 步 Decoder 的曲线：三篇样本的平方目标为 `1、−1、2`，AdamW 使用 `η=.1、ρ₁=.9、ρ₂=.99、λ=.01`；每轮按一个固定状态的整数 RNG 洗牌。第 5 步后保存参数、矩状态与步数、RNG、当前顺序及游标，再比较后续七步。全部恢复时两线重合；漏优化器会先改变更新，漏游标会先改变样本，漏 RNG 的影响要等到再次洗牌。探针隔离恢复语义；正文 Decoder 的十二步严格核对仍由配套脚本完成。

## 生成：训练目标如何进入自由运行

脚本以 `[a,b]` 为提示，取最后一行 logits 的最大项作为下一 token，追加回输入，再重复最多六次；出现 EOS 就停止。一次实际运行生成 ID `[0,1,2,0,1,2,0,1]`，即 `abcabcab`，没有在这个短预算内遇到 EOS。

这使用贪心选择，不表示训练损失只要求预测最大项；交叉熵监督完整正确类别概率。自由生成会把自己的选择作为后续上下文，而验证通常使用真实历史的教师强制（teacher forcing）。二者条件不同，因此低验证 NLL 不能保证任何提示都生成正确序列。

生成示例每次重算整个短提示，让新读者直接看清“取末行分数→选 ID→追加”的循环。脚本还对同一训练权重核对 [P10 KV cache](/principles/kv-cache/)：长九个 token 的验证输入按整体、逐 token 和 `[3,2,4]` 分块计算，拼接 logits 与完整前向在容差内一致。缓存只避免重复前向计算，不改变 checkpoint 或训练目标；缓存实现的细节由 P10 解释。

模型的位置表只支持最多 12 个输入 token。代码中的短提示和六次生成均在范围内；继续生成时必须停止、截断并重新定义可见历史，或换位置方案，不能悄悄让位置取模。

## 对照：下降后的模型胜过简单计数了吗

[P2 bigram](/principles/language-modeling/) 只根据当前 ID 预测下一个。用同三篇训练文档统计相邻 ID 的出现次数 $C_{uv}$，每格加 1 后归一化：

$$
P(t_{i+1}=v\mid t_i=u)=\frac{C_{uv}+1}{\sum_{v'}C_{uv'}+4}.
$$

这个平滑只用于估计基线概率，不是神经网络的标签平滑。用相同词表、两篇验证文档和 18 个移位目标比较 NLL，计数基线是 0.499571，训练 30 步的 Decoder 是 0.707979。后者虽比自身初始化的 1.354763 好，却**没有胜过基线**。小语料的 `abc` 转移几乎确定，一个只学转移频率的模型就很强；不能用模型规模代替实际比较。若改训练步数、tokenizer 或样本，必须重新计数并注明预算，不能把这些数字外推到自然文本。

## 迁移到文本：哪些条件必须重新声明

上一实验的四 ID、固定 11 目标和基础 Decoder 不能直接套到自然文本。`text_pretraining.py` 是第二套独立实验：六篇训练短文与两篇验证短文均为自编文本。先固定文档划分，只用训练文档拟合预切分字节 BPE，最多十六次合并。`<bos>`、`<eos>` 的 ID 在普通字节与合并项之后；模型词表大小依这张表确定。控制 ID 由程序添加，文本中相同的字面串不会自动变为控制 token。这一 tokenizer 与四 ID 表不能交换，验证 token NLL 也不能直接跨实验排名。

模型用两层、隐藏宽 24、前馈宽 48、四个 Q 头、两个 KV 头、独立头宽 8、最大上下文 64，绑定输入输出权重。查询总宽 32 不等于隐藏宽 24，正好让真实训练也覆盖这个边界。PyTorch AdamW 学习率 0.006、衰减 0.01，CPU float64 用于恢复核对；这不是推荐的大模型训练配方。

每篇文档形成 `[BOS,普通文本 ID,EOS]`，按最多 24 个目标切成窗口。相邻窗口在边界复用一个输入 ID，目标不重复；每个窗口只能看到本窗口历史，位置重新从零开始。尾窗可以更短，程序逐窗更新而不填充。训练还随机截掉窗口前零到两项作为后缀增强，所以这套实验的**每步有效目标数不固定**；不能沿用上面的 330 目标预算。

验证不使用随机裁剪，对所有窗口 NLL 求和后按真实目标数平均。输出保留每个窗口的索引、目标数与平均 NLL；短尾窗与完整窗不会获得同样总权重。当前验证共 63 个目标，初始 NLL 约 5.623874，训练 28 次后约 3.638732。这些文本共享题材，数量很小，只用于验证计算与保存流程，不能据此声称开放领域语言能力。

## 磁盘状态：恢复要跨过真正的文件边界

checkpoint 保存模型 config、权重、AdamW 状态、分词器状态、全局步数、窗口顺序、顺序游标、Python/Torch RNG，以及冻结的训练和验证文档。文档与 tokenizer 的 SHA-256 指纹在加载时重算，避免内容或 ID 映射改变后继续使用旧数据游标。词表数、顺序排列和游标范围也要检查。

先在目标目录写临时文件，再用同文件系统的原子替换更新 checkpoint；写入失败不会先删除旧 checkpoint。该流程保护进程级写入中断，不承诺突然断电时的持久化；需要耐断电时应进一步调用文件与目录同步并制定备份策略。加载使用 `weights_only=True` 与 CPU 映射，不启用任意 pickle 对象恢复。

载入模型和优化器后，最后恢复 RNG，因为实例构造本身会消耗初始化随机数。教学程序固定 CPU dtype，所有随机源只有 Python 与 Torch；若接入 NumPy、CUDA、多 worker 或 dropout，必须一并保存相应状态和数据加载器契约。[T9](/training/distributed-training/) 还解释各 rank 随机状态不一定相同。

默认运行 `python code/training/text_pretraining.py`，先更新二十次并保存磁盘文件，连续运行八次，再从该文件恢复八次。断言加载时 logits 逐位相同，之后八个损失、所有参数、游标和顺序均相同。它检验真正的文件序列化，不只是复制一个内存字典。

## 命令行：训练、恢复与生成分别运行

```sh
python code/training/text_pretraining.py --checkpoint runs/prose.pt --steps 80
python code/training/text_pretraining.py --checkpoint runs/prose.pt --resume --steps 20
python code/training/text_pretraining.py --checkpoint runs/prose.pt --generate-only --prompt "the cat" --max-new-tokens 16
```

`--steps` 是本次额外执行的更新数，所以前两次之后全局步数为 100。恢复使用 checkpoint 自带冻结文本与 tokenizer；不会重新拟合 BPE，也不从命令行替换旧语料。新训练要求 checkpoint 路径尚不存在，避免意外覆盖旧模型，并写对应的 `.tokenizer.json` 供单独查看。

可用 `--train-text train.txt --validation-text valid.txt` 启动新的训练，两份文件都采用 UTF-8、每个非空行一篇文档；程序拒绝完全重叠的文档与空集合。来源分组、近重复和评估污染仍需在进入程序前处理，见 [T8](/training/data-engineering/)，精确集合不重叠不能证明不存在所有泄漏。

生成给 prompt 前添加 BOS，prefill 后逐 token 使用缓存，采样遇 EOS 或达到预算停止。词表包含所有字节，随机生成可能不是合法 UTF-8，展示采用替换字符；P1 的严格往返检查不因此放宽。模型尚小、训练尚短，生成内容不保证可读，训练、评估与恢复才是本实验的验收对象。

## 常见误区

保存参数不等于保存可继续训练的状态；`eval()` 不等于关闭梯度；验证损失下降不等于胜过 bigram，更不等于泛化证明。同一种子也不保证恢复一致：模型重建会消耗随机数，漏掉数据游标会改变后续样本。

每步的输入是 `[a,b,c]`，目标是 `[b,c,EOS]`，只有 3 个有效目标；30 步共 90 个，而原实验是 330 个。步数相同并不代表目标预算相同。若另外两篇仍长 11 目标，必须逐步累计实际有效数，不能再用 `30×3` 或 `30×11` 概括全部更新。

</details>

<details>
<summary>只加载模型权重，重新创建 AdamW，加载后验证输出相同。为什么下一步仍会不同？</summary>

前向仅依赖权重与输入，而 AdamW 更新还依赖历史矩状态和步计数。新优化器把它们设为零，偏差校正也从第一步开始，所以同一梯度产生不同更新。需要恢复优化器状态，并核对后续一步。

</details>

<details>
<summary>为什么在内存保存 state_dict 后要深拷贝？</summary>

普通字典中的张量可能引用模型当前存储，继续训练会修改它们。深拷贝或立即序列化才能固定保存时刻。文件写入失败则是另一类风险，需要持久化协议解决。

</details>

<details>
<summary>如果把 Decoder 多训练 30 步，怎样公平地重新比较 bigram？</summary>

先声明 Decoder 总计 60 次更新、660 个有效目标。bigram 的转移计数仍只从原来的三篇**训练文档**得到，不读取验证文档；两者仍在同两篇验证文档的 18 个移位目标上报告 NLL。注明前者增加了训练预算，不能把新旧 Decoder 差别归因于模型结构。若还修改 tokenizer，则验证事件和分母改变，需要重新设计比较协议。

</details>
