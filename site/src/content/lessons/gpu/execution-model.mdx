两个长度为 100 的数组相加，Python 可以写 `c = a + b`，C++ 可以循环处理下标 0 到 99。在 GPU 上运行时，每个线程都执行同一段程序，必须根据自己的编号确定输出位置。若多个线程写 `c[0]`，会互相争抢；若没有线程写 `c[99]`，结果就不完整。

本章只要求你知道数组下标和循环。我们用 NVIDIA CUDA 建立一个可手算的执行模型：主机发起工作，grid 描述所有任务，block 描述协作组，thread 用编号确定职责，warp 解释一组线程怎样推进，SM 解释工作由哪些硬件承载。最后给出独立的 CPU 核对脚本和完整的 CUDA 入口。这里的 32-lane warp 是 NVIDIA CUDA 的具体约定，迁移到其他厂商时必须核对其执行宽度与同步规则。

## 主机与设备：谁发起工作，谁完成计算

主机（host）指运行控制代码的 CPU 及其相连内存；设备（device）在本章指 GPU 及其设备内存。这个区分首先是执行与内存的角色，不要求它们一定装在不同电路板上。GPU 内核（kernel）是一段供设备执行的函数，启动（launch）是主机向设备提交该函数及其执行配置的操作。这里的 kernel 与操作系统内核不是同一个概念。

向量加法的主机流程很具体：准备输入，在设备上申请空间，把输入送到设备，启动加法，等待结果可用，把结果取回，释放空间。设备函数只负责计算。不要把这个流程想成把整个 Python 程序搬进显卡；文件读取、参数检查、控制分支等工作仍然由主机组织。

数学任务是对每个 $i\in\{0,\ldots,N-1\}$ 计算

$$
c_i=a_i+b_i.
$$

这里 $N$ 是数组元素数，三个数组形状都是 $(N,)$。每个输出只依赖相同下标的两个输入，因此任务之间没有先后依赖。比如输入为 $(1,2,3)$ 和 $(10,20,30)$，三个任务各自得到 11、22、33。完成顺序改变，输出仍然相同。这是最适合建立执行模型的起点。

CPU 循环把“下一个下标”藏在迭代过程中；GPU 程序通常让执行者从自己的编号算出下标。你写的是每个执行者的工作说明，而不是由主机为每个元素分别调用一次函数。一次启动就能描述许多线程的工作，执行者数量通过启动配置指定。

启动通常对主机是异步的：主机在提交后可以继续运行，不能仅凭调用返回就认为设备已经写完输出。完整示例在启动后检查错误，并调用 `cudaDeviceSynchronize()` 等待设备工作完成。这种明确等待适合第一份正确性示例；关于 stream、重叠和计时的安排见 [G4 GPU 的测量与优化](/gpu/measurement/)。

## Thread、block、grid：先给任务编地址

线程（thread）是执行同一 kernel 的一个实例，具有自己的编号和局部状态。两个线程都执行 `float v = a[i]`，变量名相同，但它们的 `i` 和 `v` 可以不同。逻辑上的线程不是一个永久绑定的算术单元，也不是一条需要由操作系统逐个创建的 CPU 线程。

线程块（thread block，后文简称 block）把一组线程组织在一起。块内线程可以使用该块的 shared memory，并通过规定的屏障协作；它们不必同时执行每条指令。网格（grid）是一次 kernel 启动的所有 block。同一个 grid 的各个 block 具有相同的线程维度；索引从零开始。

一维情况下，CUDA 给每个线程提供四个内置量：`threadIdx.x` 是块内线程编号，`blockIdx.x` 是块编号，`blockDim.x` 是每块线程数，`gridDim.x` 是 grid 中的块数。它们不是用户为每个线程手工填写的参数，而是执行配置产生的身份信息。`Dim` 表示尺寸，`Idx` 表示编号，混用两者是常见错误。

用 $T_b$ 表示每个 block 的线程数，$G$ 表示 block 数，$b$ 表示块编号，$t$ 表示块内线程编号。此处 $T_b$ 是线程块大小，后续讲数据 tile 时会明确区分元素数。范围是 $0\le b<G$、$0\le t<T_b$。全局任务编号为

<KeyEq label="一维任务归属">

$$
i=bT_b+t.
$$

</KeyEq>

乘法把前面所有块的线程数跳过，再加上当前块内部的偏移。例如 $T_b=64$，块 0 的编号覆盖 0–63，块 1 覆盖 64–127；块 1 的线程 7 得到 $i=1\times64+7=71$。相邻块的区间接起来而不重叠，所以只要每个合法线程都执行一次，输出就有唯一负责人。

唯一性的证明也很短：对任意非负整数 $i$，除以 $T_b$ 的商与余数唯一。商给出 $b=\lfloor i/T_b\rfloor$，余数给出 $t=i\bmod T_b$。这比“看起来没有冲突”更可靠；后面改变块大小时，也仍然可以用同一个证明检查。

## 向上取整与尾部：128 个线程怎样处理 100 个元素

数组长度通常不是块大小的整数倍。要覆盖全部元素，需要的 block 数为

$$
G=\left\lceil\frac{N}{T_b}\right\rceil
=\left\lfloor\frac{N+T_b-1}{T_b}\right\rfloor\quad(N\ge0,\ T_b>0).
$$

第二个写法适合非负整数算术，但实现还要防止加法溢出。我们的示例使用固定的小尺寸，后续支持任意外部尺寸时应使用足够宽的整数并验证边界。$N=100$、$T_b=64$ 时，$G=2$，逻辑线程共 128 个。元素只有 100 个，多出的编号 100–127 共 28 个，必须禁止它们访问数组。

```cpp
__global__ void add_once(const float* a, const float* b, float* c, size_t n) {
    const size_t i = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}
// n=100: add_once<<<2, 64>>>(a, b, c, n);
```

`__global__` 标识供主机启动、在设备执行的函数。三尖括号中的第一项是 block 数，第二项是每块线程数。强制转换放在乘法之前，让乘法以 `size_t` 进行；在乘法之后才转换，不能补救已经发生的整数溢出。`i < n` 同时保护两个读取和一次写入，而不是只保护输出。

块 1 的线程 35 负责 $i=99$，应当执行；线程 36 负责 $i=100$，应当跳过。跳过并不表示系统少启动了一个线程：线程仍在配置中，只是没有执行有效数据的加法。因此“启动线程数”和“有效元素数”是两个量。

实验中的每个格子标记全局元素编号，展示当前 block。绿色格子可以读写，橙色格子在数组边界外；空轮廓只是固定绘图位置，并非启动线程。把每块线程数从 64 改成 32，长度仍为 100，会得到四个 block 和同样的 28 个尾部线程；改成 16，则是七个 block、112 个线程和 12 个尾部线程。尾部变少不代表总时间一定变短，调度、访存和资源也会影响结果。

零长度是另一个需要明确处理的边界。$N=0$ 时没有有效输出，主机直接跳过启动，不能把 `<<<0, threads>>>` 当成合法的空操作。单元素则可以启动一个 block，让一个线程工作，其余线程由条件挡住。真实张量算子经常遇到空批或很短的维度，边界不是只为练习而设。

## 软件与硬件：grid 不等于同时占满全部核心

流式多处理器（Streaming Multiprocessor，SM）是 NVIDIA GPU 承载线程工作的硬件单元，其中包含寄存器资源、执行单元和 warp 调度器等。一个 block 的线程在同一个 SM 上执行；SM 能否同时容纳多个 block，取决于线程数、寄存器、shared memory 以及架构上限。

调度实验提交六个 block，假设两个 SM 各有两个教学槽位，每块 64 个线程、两个 warp。步骤 2 中，B0 的 warp 0 等待数据，仍占据驻留资源；同一 SM 上 B2 的 warp 0 可以发射指令。继续推进，可以看到 B1 先结束，释放的槽位随后接纳 B4。编号较大的块可以先结束，待执行、驻留和可运行是三种不同状态。这里没有跨 block 的数据依赖，步骤也不代表真实时间或某款 GPU 的发射策略。

可以回读 [GPU 导读](/gpu/) 的整体模型，把软件组织与硬件连接起来：线程局部状态使用 SM 的寄存器资源，执行单元负责计算，shared memory 用于块内交换，L1、L2 缓存与显存参与数据访问。它们不是可以互相替换的层次；尤其等待数据的 warp 不会因为暂时没有发射就释放全部资源。详细内存路径与作用域在 [G2](/gpu/memory-and-sync/) 展开。

读图时先看上半部分：编号是程序的身份。再看下半部分：同一个 SM 可能承载块 0 和块 2，另一 SM 承载块 1。grid 可以比 SM 数大得多，尚未获得资源的 block 后续再执行。运行在更多 SM 的 GPU 上时，正确的任务映射不应变化，只是硬件可以承载的并发工作不同。

因此 `gridDim.x = 1000` 的含义是“提交 1000 个块”，不是“GPU 有 1000 个 SM”，更不是“1000 个块此刻全部驻留”。CUDA 中常说的核心数也不能直接作为线程数：线程描述程序状态，执行单元负责执行指令，两者会通过调度复用。把一百万线程想成一百万份永久占用的硬件，心智模型就会走偏。

普通 kernel 不保证 block 按编号开始或结束。即使某次实验打印出 0、1、2、3，也不能据此推出下一次保持顺序。设备、负载或资源分配改变就可能改变观测。正确程序必须允许 block 以任意顺序执行。

这会排除一种危险写法：块 0 自旋等待块 1 写标志，而块 1 只有在块 0 释放资源后才能被调度。等待者占住资源，生产者没有运行机会，程序可能不再前进。全局内存可被所有块寻址，并不意味着所有块同时运行，也不自动建立正确的先写后读关系。

需要所有块完成一个阶段再进入下一阶段时，初学者应把工作拆成同一 stream 中有序的两次 kernel；特殊的协作式启动有单独的适用条件。内存可见性、原子操作与屏障在 [G2 GPU 的内存与同步](/gpu/memory-and-sync/) 展开。此处先记住：数据地址的可达性、执行者的可驻留性和同步的保证是三件事。

## Warp 与 lane：同一段程序允许不同路径

在 NVIDIA CUDA 中，block 的线程按块内线性编号划分成每组 32 个的线程束（warp）。线程在 warp 内的位置称为 lane，编号为 0–31。对块内线性编号 $t$，有

$$
w=\left\lfloor\frac{t}{32}\right\rfloor,
\qquad \ell=t\bmod32.
$$

$w$ 是块内 warp 编号，$\ell$ 是 lane。64 线程的块有两个 warp，编号 0–31 属于第一个，32–63 属于第二个。40 线程的块同样有两个 warp，但最后一个只有 8 个真实线程位置；不存在的另外 24 个 lane 不会从下一 block 补进来。warp 的组边界不会跨 block。

单指令多线程（Single Instruction, Multiple Threads，SIMT）表示同一 warp 的线程从同一程序出发，硬件以活跃线程集合推进指令。每个线程仍可以持有不同数据，走不同条件分支。它与“每个线程完全独立占一套指令硬件”的想象不同，也不能简单等同于一条固定宽度的 CPU 向量指令。

例如 `if (lane < 16) A(); else B();` 把 32 个 lane 分成两个集合。执行 A 路径时，属于 B 的 lane 对这条路径不活跃；执行 B 时反过来。这个现象叫 warp 分歧（warp divergence）。只有一组 lane 满足条件时，程序仍然正确，变化的是哪些位置参与各条路径。

<WarpBranchLab client:visible />

实验显示两个路径的活跃集合。阈值为 16、有效 lane 为 32 时，A 与 B 各有 16 个；改成“偶数 lane”，A 变成 0、2、4……30，计数仍是 16。每个有效 lane 恰好落在一个集合里。把阈值设为 32，则所有有效 lane 只走 A；设为 0，只走 B。

这里画的是源程序条件的集合，不能把“非空路径数为 2”解释成“运行时间恰好翻倍”。两条路径的指令长度可能不同，编译器可能用谓词指令处理短分支，访存等待与调度也影响时间。要讨论实际指令，需看编译后的代码；要讨论速度，需测量。图里没有捏造这两类信息。

尾部检查也是分歧的一种来源。在 100 元素、64 线程每块的示例中，块 1 的第一个 warp 负责 64–95，全部有效；第二个负责 96–127，只有 lane 0–3 执行加法。把 28 个边界外 lane 屏蔽是正确性所需，不能为了消除分支而直接删除边界检查。

另一个容易被忽略的区别是“最后一个 warp 没有实际线程的 lane”与“线程存在但本路径不活跃的 lane”。40 线程的块尾部 24 个位置属于前一种；64 线程块处理尾部数据，28 个线程跳过加法属于后一种。在需要指定参与 mask 的 warp 操作中，这个区别会直接影响同步契约。

### 同一个 warp 为什么也需要明确同步

不要把 warp 的分组理解为“一个线程写完 shared memory，邻居必然已看到”。从计算能力 7.0 起，NVIDIA 的独立线程调度（Independent Thread Scheduling）能够保存线程级执行状态；同一 warp 内线程的推进不能靠旧式隐含锁步假设建立数据依赖。

如果一个线程要读取另一个线程刚写的数据，必须依据通信范围使用合适的同步或具有明确定义的 warp 原语。`__syncwarp(mask)` 的参与集合需要正确，跨 warp 的块内协作通常需要 block 屏障。仅把代码放进同一 `if`，或观察到它在某张卡上能运行，都不是同步证明。

对于当前向量加法，线程只读取自己的输入，写自己的输出，没有线程间数据交换，因此根本不需要线程屏障。判断需不需要同步的方式是追踪“谁写、谁读、是否跨执行者”，而不是看到 GPU 代码就加一个屏障。

## 二维与三维编号：坐标、内存偏移、warp 编号分别计算

矩阵用二维坐标更容易表达职责。设矩阵有 $R$ 行、$C$ 列，按行主序存放：同一行的相邻列在内存中相邻。block 的 x 维取 $T_x$，y 维取 $T_y$，线程坐标为 $(t_x,t_y)$，块坐标为 $(b_x,b_y)$。令 x 对应列、y 对应行，得到

$$
c=b_xT_x+t_x,\qquad r=b_yT_y+t_y,
\qquad p=rC+c.
$$

$r,c$ 决定逻辑矩阵元素，$p$ 是连续存储中的元素偏移；字节偏移还要乘每元素字节数。这三者不要混写。合法条件是 $r<R$ 且 $c<C$，仅检查 $p<RC$ 不够：边界外的一列可能算出落在下一行的合法偏移，进而重复写入。

以 $5\times7$ 矩阵、$4\times2$ block 为例，grid 是 $2\times3$。block $(1,2)$ 从行 4、列 4 开始：线程 $(0,0)$ 负责 $(4,4)$，偏移 $4\times7+4=32$；线程 $(2,0)$ 负责 $(4,6)$，偏移 34；线程 $(3,0)$ 的列为 7，越界；y 为 1 的线程行号为 5，也全部越界。总共启动 $2\times3\times4\times2=48$ 个线程，合法矩阵元素有 35 个。

图的三层分别是 grid 中的 block、选中 block 内的 thread、以及它负责的矩阵位置。底层保留一列和一行尾部，使越界线程也有可观察的位置；有效格中的数字是行主序偏移，蓝色区域表示当前 block 的覆盖。点选块与线程或调整坐标，就能逐层追踪同一个执行者。

初始选择故意给出一个反例：block $(1,0)$ 的 thread $(3,0)$ 得到 $(r,c)=(0,7)$。列号已经越界，但 $p=0\times7+7=7<35$，仅检查偏移会通过。这个位置在有效矩阵中实际上是 $(1,0)$，会与另一线程的职责重叠。因此合法地址不等于合法逻辑坐标，必须检查两条坐标边界。再选择 block $(1,2)$ 的 thread $(2,0)$，可核对最后一个合法元素的偏移 34。

warp 分组使用的则是**块内**线性线程号。在三维 block 中，x 维变化最快：

$$
t=t_x+T_x(t_y+T_y t_z).
$$

这来自逐行展开：每推进一次 y，跳过 $T_x$ 个线程；每推进一次 z，跳过 $T_xT_y$ 个线程。二维时令 $t_z=0$。再用 $t$ 计算 warp 与 lane，不能直接用矩阵偏移 $p$，因为后者还包含块坐标和矩阵宽度。

这张轴测图使用 $8\times4\times2$ 的逻辑 block。上、下两层分别代表 z 为 1、0；下方平面展开当前 z 切片，并标出线性线程号。x 加一，编号加一；y 加一，编号加八；z 加一，编号加 32。因此初始坐标 $(0,0,1)$ 的编号为 $0+8(0+4\times1)=32$，对应 warp 1、lane 0。把 z 改成 0，其他坐标不动，编号就减去 32。图的深度来自坐标投影，不描述芯片中核心的物理位置。

例如 $8\times8$ 的二维 block 有 64 个线程。编号 32 的线程坐标是 $(0,4)$，属于 warp 1、lane 0。warp 0 经过 y 为 0–3 的四行，每行八个线程；它不是“一整行”。若 block 改成 $32\times2$，每个 warp 才恰好对应块内一行。这就是为什么研究矩阵访存时，必须先确定真实的 lane 到地址映射。

三幅图都只有 64 个逻辑线程，绿色与蓝色分别表示 warp 0、warp 1，虚线位于线性编号 31 和 32 的分界。滑块始终选择同一个线性编号，所以 warp 与 lane 不变，但二维坐标随布局改变。选择编号 32，可看到它分别位于 $(0,4)$、$(0,2)$、$(0,1)$；选择 31，则分别位于 $(7,3)$、$(15,1)$、$(31,0)$。这也说明 warp 在三种布局中分别跨四行、两行和一行。颜色只说明分组，没有承诺线程同时运行或自动同步。

把线程二维布局换成 $16\times4$ 仍有 64 个线程，但相邻 lane 跨行的位置发生了变化。数学结果可以完全一致，访存和分支分组却可能不同。二维 block 是编址的便利方式，不表示 GPU 上的算术单元也按这个矩阵摆放。三维 block 同理，不是物理的三维核心阵列。

## Grid-stride loop：线程数量与数据数量可以分开

“每个线程处理一个元素”是方便的初始映射，并非必须的规则。数据非常长时，可以启动有限数量的 block，让每个线程反复处理间隔固定的元素。这叫 grid-stride loop：步长跨过整个 grid 的逻辑线程数。

设启动 $G$ 个 block，每块 $T_b$ 个线程，总逻辑线程数 $P=GT_b$。线程起始编号为 $i_0=bT_b+t$，随后处理

$$
i_k=i_0+kP,\qquad k=0,1,2,\ldots,\quad i_k<N.
$$

例如 $N=100$，只启动两个 16 线程块，$P=32$。线程 0 处理 0、32、64、96；线程 3 处理 3、35、67、99；线程 4 处理 4、36、68，然后停止。线程多次工作，但各线程之间仍然不重叠。

证明沿用商余数：任意 $i$ 对 $P$ 取余得到唯一 $i_0$，商得到唯一迭代轮次 $k$。所以整个循环既覆盖全部下标，又保持唯一写入。每轮内相邻线程仍处理相邻元素，便于下一章分析访存。

```cpp
const size_t start = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
const size_t stride = size_t(blockDim.x) * gridDim.x;
for (size_t i = start; i < n; i += stride) {
    c[i] = a[i] + b[i];
}
```

grid-stride 是同一次 kernel 内每个线程的普通循环，不会在每轮重新启动 kernel，也没有给所有线程加全局轮次屏障。某个线程可以先处理下一轮，另一个线程仍在上一轮；当前计算因为元素独立而不受影响。如果下一轮依赖别的线程的上一轮结果，这段循环本身不提供所需同步。

独立的数据任务也可以由一个线程负责多个相邻元素，或由一个 block 负责整行，映射要根据复用和协作需求选择。grid-stride 的价值是把覆盖正确性与启动规模解耦；它不是“任意小 grid 都更快”的性能结论。完整示例把块数限制为 SM 数的四倍，这只是展示可调度规模的教学选择，不是设备通用的最佳配置。

## 回到 LLM：用依赖决定工作划分

逐元素激活 `y[i] = sigmoid(x[i])` 与向量加法相似：每个输出独立，标量线程映射或 grid-stride 都容易核对。但一次 RoPE 旋转需要同一对通道的两个值。可以让一个线程负责一对，避免两个线程覆盖彼此的输入；也可以先把需要的旧值完整读取到局部状态，再设计协作。这里关键是明确原地更新时的数据依赖，不能仅套用“一线程一元素”。

RMSNorm 的每个输出还依赖同一行的平方均值。线程负责一个元素只是输出分工，不能让它独自获得整行统计量。需要把同一行的工作组织成能交换部分结果的组，再进行归约。softmax 同样需要行最大值与指数和。读完 [G2](/gpu/memory-and-sync/) 的通信规则后，才能把这类行计算实现正确。

矩阵乘的一个输出依赖整段点积，多个输出又复用输入。单纯按输出编号启动线程可以得到正确的朴素实现，但会反复读取同一数据。[G3 Kernel 的设计](/gpu/kernel-design/) 会用 tile 描述一个协作组的输出与输入复用。先回答数据依赖，再决定 block 形状，比从“256 线程是不是标准答案”开始更可靠。

可以在纸上为任何算子填三行：每个输出的负责人是谁，它需要哪些输入，哪些输入由其他执行者产生。第一行检查唯一写入，第二行检查地址与边界，第三行检查同步。正确性清楚以后，再进入 [S2 单卡的上限](/systems/accelerator/) 的带宽与算力讨论。

## 常见误区

- **线程数等于 GPU 核心数。** 线程是逻辑程序实例，硬件通过调度承载许多线程；启动数量不描述物理执行单元数量。
- **同一个 block 内所有线程逐条同时执行。** block 是协作与资源分配范围，包含多个 warp；跨 warp 交换数据必须满足同步规则。
- **同一 warp 可以靠隐含顺序交换数据。** lane 分组不能代替同步契约，独立线程调度尤其会暴露这种假设。
- **二维 block 的每一行都是 warp。** 先按 x 最快变化展开，再按 32 分组；一行宽度为 8 时，一个 warp 跨四行。
- **block 编号就是执行顺序。** 编号只标身份，普通 grid 必须允许任意 block 顺序；全局自旋可能阻塞尚未调度的生产者。
- **多启动的尾部线程没有代价，所以任意块大小都一样。** 结果可以一样，资源占用与调度可以不同；这属于测量问题，不能从覆盖证明推断。

## 练习与核对

<details>
<summary>100 个元素、每块 64 个线程：最后一个有效元素属于哪个 block、哪个 thread、哪个 lane？</summary>

99 除以 64，商为 1、余数为 35，所以属于 block 1 的 thread 35。块内线性编号 35 除以 32，得到 warp 1、lane 3。其后的 thread 36–63 共 28 个不访问数组。这里 lane 用块内编号计算，不能直接把全局元素 99 对 32 取余来推断一般情况。

</details>

<details>
<summary>二维 block 为 8×8，编号 31 与 32 的坐标分别是什么？</summary>

x 维最快变化，所以编号 31 是 $(7,3)$，编号 32 是 $(0,4)$。前者在 warp 0 的 lane 31，后者在 warp 1 的 lane 0。这两个线程在矩阵图上位于相邻的两行，并不因此属于同一 warp。

</details>

<details>
<summary>把 100 元素加法从每块 64 线程改成 16，哪些量改变，哪些正确性条件仍需成立？</summary>

一次处理一个元素时，block 数从 2 变成 7，线程数从 128 变成 112，尾部从 28 变成 12。仍必须覆盖下标 0–99，每个位置恰好写一次，并在访问前检查边界。对于纯独立加法，输出不应变化。哪一种更快需要真实设备与明确计时边界，不能只比较尾部数。

</details>

<details>
<summary>只启动 32 个逻辑线程处理 100 个元素，线程 7 负责哪些下标？为什么不会与线程 8 重复？</summary>

grid-stride 为 32。线程 7 处理 7、39、71，下一项 103 越界；线程 8 处理 8、40、72。前一组下标除以 32 的余数恒为 7，后一组恒为 8，所以不会重复。所有余数 0–31 都有执行者，因此仍能覆盖全数组。

</details>

<details>
<summary>为什么不能让 block 0 在循环里等待 block 1 写完标志，再读取它的结果？</summary>

block 1 不保证已经驻留或能够立即被调度。block 0 可能占着生产者所需资源等待，导致无法前进；即使调度碰巧允许并发，普通读写标志也没有自动提供正确的跨线程通信。先把两阶段拆成同一 stream 中有序的两个 kernel，再讨论确实需要的特殊同步方案。

</details>
