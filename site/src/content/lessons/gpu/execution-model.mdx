设两个数组各有 100 个元素，我们要计算 $c_i=a_i+b_i$。CPU 循环逐个推进 $i$；CUDA kernel 让许多 thread 执行同一段代码，各自用编号确定 $i$。

阅读本章只需要数组下标和整数除法。你将从启动配置算出每个输出的写入者和越界线程，再分析增加线程数对吞吐的影响。

以下 thread、block、grid、warp 和 SM 均按 NVIDIA CUDA 的定义使用。warp 宽度为 32 是该平台的规定，迁移到其他 GPU 平台时需重新核对。

## 给输出编号：100 个元素由谁写

Host 是发起计算的 CPU 侧程序，device 是执行 kernel 的 GPU。Host 准备输入并启动一次 kernel；kernel 是在 device 上由许多 thread 执行的函数。这个调用通常异步返回，调用返回并不意味着输出已经写完。完整示例在读取结果前同步；计时与 stream 留到 [G4](/gpu/measurement/)。

一次启动的所有 thread 组成 grid。grid 分为若干 block，每个 block 有相同数量的 thread。block 是协作和资源分配的单位，thread 是执行 kernel 的一个逻辑实例。令每块有 $T_b=64$ 个 thread，block 编号为 $b$，块内编号为 $t$，则

<KeyEq label="一维输出归属">
$$
i=bT_b+t,\qquad 0\leq t<T_b.
$$
</KeyEq>

CUDA 中分别写作 `blockIdx.x * blockDim.x + threadIdx.x`。`blockDim.x` 是尺寸 64，不是编号；`threadIdx.x` 从 0 到 63。block 0 覆盖下标 0–63，block 1 覆盖 64–127。对输出 99，$99=1\times64+35$，所以由 block 1 的 thread 35 负责。

为什么不会重复写？任意非负整数 $i$ 除以 64 都有唯一的商和余数：商是 $b$，余数是 $t$。反过来，若漏掉某个 block 或 thread，那个下标就没有负责人。这份商余数证明只解决**归属**，还没有保证越界安全。

## 尾部边界：128 个位置只用 100 个

所需 block 数是 $G=\lceil N/T_b\rceil$。当 $N=100$、$T_b=64$ 时，$G=2$，启动了 $GT_b=128$ 个逻辑 thread，只有下标 0–99 有效。block 1 的 thread 35 写最后一个元素，thread 36–63 对应 100–127，必须跳过读取和写入：

```cpp
__global__ void add(const float* a, const float* b, float* c, size_t n) {
    const size_t i = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}
// n=100: add<<<2, 64>>>(a, b, c, n);
```

`size_t` 转换放在乘法前，避免先以较窄整数相乘再转换。`i < n` 同时保护两次读和一次写。$N=0$ 时 host 不启动 kernel；`<<<0, 64>>>` 不能当作“什么也不做”的通用写法。

<ThreadIndexLab client:visible />

在图中选 block 1，核对 99 和 100 分别在哪个 thread。再把每块数量改为 16：需要 7 个 block，总共 112 个位置，尾部剩 12 个。尾部减少了，但 block 数增加了。两种配置的结果应相同；仅凭这两项计数不能判定哪一种快。

## Warp：边界分支影响哪些 lane

一个 block 内的 thread 按块内**线性**编号分成 warp，每组最多 32 个。thread 在 warp 内的位置叫 lane。对本例的块内编号 $t$，warp 编号为 $\lfloor t/32\rfloor$，lane 为 $t\bmod32$。64-thread block 有两个 warp；thread 35 位于 warp 1、lane 3。

SIMT（单指令多线程）让一个 warp 的 thread 执行同一份 kernel，同时保留各自的数据和分支条件。若同一 warp 的 lane 走不同路径，执行某一路径时其他 lane 不参与该路径，这称为 warp 分歧。不同 warp 的路径选择不构成同一个 warp 内的分歧。

本例中 block 1 的 warp 0 处理 64–95，32 个 lane 都有效；warp 1 处理 96–127，只有 lane 0–3 执行加法。其余 28 个 thread 仍属于已启动的 block，却被边界条件挡住。这里的边界分歧是**正确性所需**，不能为了消除它直接删除条件。

<WarpBranchLab client:visible />

把实验里的条件切换为 `lane < 16`：一个完整 warp 中各有 16 个 lane 走两条路径。再试“偶数 lane”：参与数量仍是 16，但活跃位置交错。图只显示逻辑活跃集合；实际指令可能被编译器改写，因此“两条路径”不能直接换算成“恰好两倍耗时”。

40-thread block 有两个 warp，第二个 warp 只含 8 个 thread；缺少的 24 个位置不是别的 block 借来的 lane。它与本例的“thread 存在但跳过加法”不同。即便同属一个 warp，也不能靠隐含锁步来证明跨 thread 通信正确；需要交换数据时用 [G2](/gpu/memory-and-sync/) 的同步规则。本例各 thread 只写自己的 $c_i$，所以不需要屏障。

## SM：为什么 128 个 thread 不会占据 128 个核心

SM（Streaming Multiprocessor）是承载 block 的硬件单元。block 被安排到某个 SM 后，寄存器和 shared memory 等资源供该 block 使用；SM 从可运行的 warp 中选择指令发射。grid 的两个 block 是**软件任务数**，与 GPU 有多少 SM 或算术单元无关。普通 block 的先后顺序没有保证，程序不能让 block 0 自旋等待尚未获得资源的 block 1。

<BlockScheduleLab client:visible />

实验假设两个 SM、每个 SM 有两个教学槽位。观察 B0 的一个 warp 等数据时，B2 的 warp 可以推进；B0 虽暂时没有发射，仍占着驻留资源。这个模型说明了三个不同状态：block 尚未获分配、warp 已驻留但在等待、warp 可发射。它不模拟某款芯片的周期数。

若一次内存读取尚未返回，该 warp 的依赖指令要等待。SM 可发射别的可运行 warp，使**单位时间完成的工作量**（吞吐）增加；原读取从发出到返回的**延迟**没有因此缩短。若只有两个很短的 block，本例可能无法给许多 SM 提供工作。把 $N$ 扩大后，更多 block 才有机会让设备持续处理，最终效果还取决于带宽、发射开销与资源。

Occupancy 指一个 SM 上已驻留 warp 数占该 SM 可驻留 warp 上限的比例。寄存器、shared memory、每块 thread 数和架构上限都会限制驻留；这个比例不是“正在执行指令的 lane 百分比”，也不是整张 GPU 的利用率。高 occupancy 增加隐藏等待的机会，但超过足够隐藏等待的水平后，不保证吞吐继续上升。算资源上限和测时间的方法见 [G4](/gpu/measurement/)；本章的 100 元素例子只用来区分这些量，不能拿它的 CPU 索引检查推断 GPU 速度。

### 当数据多于启动的 thread

一个 thread 也可以处理多个元素。仍处理 100 个元素，只启动两个 16-thread block，此时 grid 共 $P=32$ 个 thread。编号为 $i_0$ 的 thread 每次跨过整个 grid，处理 $i_k=i_0+kP<N$。例如 thread 3 负责 3、35、67、99。

任意有效下标除以 32，余数给出唯一的 $i_0$，商给出循环轮次，所以仍然没有漏写或重复写。这叫 grid-stride loop。各 thread 独立执行自己的循环，轮次之间没有跨 block 屏障。

```cpp
const size_t start = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
const size_t stride = size_t(blockDim.x) * gridDim.x;
for (size_t i = start; i < n; i += stride) c[i] = a[i] + b[i];
```

两种映射的输出相同，但循环次数、启动规模与资源使用不同，性能需要测量。[归约实践](/gpu/reduction-practice/) 会让每个 thread 先累加自己的一串输入，再在 block 内合并。

## 迁移：从一维下标到矩阵坐标

向量加法中每个输出独立；在矩阵里，先确定输出的**逻辑坐标**，再算存储偏移。设行主序矩阵有 $R$ 行、$C$ 列，用 $T_x\times T_y$ 的二维 block，让 x 对应列、y 对应行：

$$
c=b_xT_x+t_x,\qquad r=b_yT_y+t_y,\qquad p=rC+c.
$$

只有 $r<R$ 且 $c<C$ 才能访问元素。比如 $5\times7$ 矩阵使用 $4\times2$ block，block $(1,0)$ 的 thread $(3,0)$ 算出 $(r,c)=(0,7)$，列已越界。但偏移 $p=7<35$，只检查 `p < R*C` 会误写下一行的元素。

分析 warp 内的访问时，还要计算块内线性编号 $t=t_x+T_xt_y$。warp 按这个编号每 32 个 thread 分组，矩阵行和偏移 $p$ 不决定分组。这为 [G2 的访存分析](/gpu/memory-and-sync/) 做准备。

默认选中 block $(1,0)$ 的 thread $(3,0)$。矩阵的灰色尾格对应越界列，即使线性偏移 7 看起来合法，也不能执行访问。将 thread x 改为 2，行列检查才通过；再选最右下的 block $(1,2)$，核对最后一个合法元素 34 的负责人。

## 常见误区

- **线程数等于核心数。** Thread 是逻辑程序实例，SM 通过调度承载它们。
- **block 编号决定执行顺序。** 编号确定输出归属，普通 grid 不保证跨 block 的先后。
- **尾部 lane 空闲，所以可以删去边界判断。** 条件保护数组读写，分歧代价不能凌驾于正确性。
- **高 occupancy 就是高吞吐。** 驻留数、可发射工作、设备瓶颈与实测时间是不同量。

## 练习与核对

<details>
<summary>长度改成 130，每块仍有 64 个 thread。最后一个元素与尾部 warp 分别是什么情况？</summary>

$G=\lceil130/64\rceil=3$。最后一个元素 129 属于 block 2 的 thread 1，即 warp 0、lane 1。该 block 的 warp 0 只有 lane 0–1 有效，warp 1 全部跳过；共启动 192 个 thread，62 个越界。编号计算和边界判断没有改变。
</details>

<details>
<summary>一个 $5\times7$ 矩阵用 $4\times2$ block。block $(1,2)$ 的 thread $(2,0)$ 写哪里？只检查线性偏移安全吗？</summary>

$r=2\times2+0=4$，$c=1\times4+2=6$，偏移 $p=4\times7+6=34$，这是最后一个合法元素。只检查 $p<35$ 不安全：同一布局下 block $(1,0)$ 的 thread $(3,0)$ 有 $c=7$，却得到看似合法的 $p=7$。必须分别检查行列。
</details>

<details>
<summary>若 100 元素数组的两块恰好都在同一个 SM 上，结果会变吗？把每块线程数改成 16 会更快吗？</summary>

不会变：每个合法 $i$ 的商余数归属只依赖启动配置，block 的实际分配和顺序不影响独立加法。16-thread 配置需要 7 块、112 个逻辑 thread，尾部更少，但调度、warp 利用和访存表现也会变化；没有设备测量不能断定更快。
</details>
