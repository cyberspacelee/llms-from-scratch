## 内存层次：先区分谁能看到数据

CPU 程序里的局部变量、数组和缓存，到了 GPU 上仍然存在，但“局部”“共享”这些词必须附带作用域。同一段 kernel 代码在许多线程中执行，变量 `sum` 通常代表每个线程各自的状态；`__shared__` 数组代表同一 block 内的协作存储；`cudaMalloc` 分配的数组则可由不同 block 的线程访问。

| 存储或机制 | 谁可以访问 | 常见用途与限制 |
| --- | --- | --- |
| 寄存器（register） | 持有该值的线程 | 索引、临时值、累加器；实际分配由编译器决定，数量影响驻留资源 |
| 共享内存（shared memory） | 同一 block 的线程 | 交换结果、复用 tile；容量有限，block 结束后其内容不再属于该 block |
| 全局内存（global memory） | 获得指针且合法访问的设备线程 | 参数、激活、中间输出；分配通常跨多个 kernel 存活 |
| L1、L2 缓存 | 由硬件管理 | 缓存数据，降低部分重复请求的代价；具体缓存路径与架构有关 |
| 本地内存（local memory） | 一个线程私有 | 可能存放寄存器溢出或编译器不能留在寄存器里的数组；不是片上寄存器的同义词 |

“私有”描述可见性，“片上”描述存放位置，不能互相替代。一个线程的 local memory 地址空间可以有很强的隔离性，却仍通过设备内存及缓存路径访问。声明一个大局部数组也不保证它都放在寄存器里。实际结果要检查编译器资源报告和 profiler，而不是根据 C++ 变量的作用域猜测。

同样，L1 命中不能替代同步。缓存回答“从哪儿取到这次数据”，同步回答“程序是否已经保证写在读前面”。如果两个线程没有建立必要的顺序，偶尔读到期望值只说明某次调度碰巧如此。共享内存也不会因为位于 SM 上就自动解决竞态。

先设想一行 RMSNorm：每个线程读取一部分隐藏状态，在私有累加器里算平方和，然后把部分和放进共享内存，最后所有线程使用同一个归约结果。这一路同时需要私有状态、block 内交换和全局输入输出。选择存储层次的方法是追问：这个值需要由谁共享，需要活到什么时候，会被读取几次？

## 合并访问：看一条指令的地址集合

合并访问（coalesced access）讨论的是**同一 warp 的一次内存访问指令**。不要把它误解成“整个 kernel 的数组连续”，也不要只看一个线程连续读了什么。一个线程连续读取一列，仍可能让同一时刻的 32 个线程访问互相很远的地址。

采用一个限定清楚的模型：计算能力 6.0 及以上的 NVIDIA 设备，32 个活跃 lane 各读取一个自然对齐的 `float32`，数组基址至少按 32 字节对齐。用 32-byte 地址段（sector）覆盖此次请求。设 lane 编号为 $\ell\in\{0,\ldots,31\}$，元素偏移为 $o$，相邻 lane 的元素步长为 $s$，从基址开始的字节地址是

$$
a_\ell=4(o+s\ell),\qquad q_\ell=\left\lfloor\frac{a_\ell}{32}\right\rfloor.
$$

$q_\ell$ 是地址段号，每个段包含 8 个 `float32`。一个请求覆盖的段数是段号集合的大小，而不是 lane 数，也不是最大段号：

<KeyEq label="先列地址，再取段号集合">
$$
N_{\mathrm{sector}}=\left|\{q_\ell:\ell\text{ 参与此次访问}\}\right|.
$$
</KeyEq>

先取 $s=1,o=0$。lane 0 到 7 读取元素 0 到 7，字节地址从 0 到 28，都在段 0；lane 8 到 15 在段 1，接着是段 2、3。32 个元素一共请求 128 字节，覆盖 4 个段，总覆盖也是 128 字节。这是地址布局利用完整的例子。

再取 $s=1,o=1$。现在读取元素 1 到 32。最前面的段只用元素 1 到 7，末尾的元素 32 落入段 4，于是覆盖集合是 $\{0,1,2,3,4\}$。请求数据仍是 128 字节，却覆盖 160 字节。偏移只增加了一个元素，整个 warp 跨过了段边界。

如果 $s=2,o=0$，元素号为 0、2、4、…、62，段号 0 到 7 每个都出现，覆盖 8 段，段覆盖为 256 字节。取 $s=8$，每个 lane 正好跨过一个段，只使用各段中的一个元素，共覆盖 32 段，也就是 1024 字节。此时 128 字节的独立读取分散得很开。

不能根据 4 段和 5 段就断言运行速度必定相差 $4/5$。相邻 warp 可能复用同一缓存段，某些数据已经在缓存里；指令吞吐、写入、启动开销和其他瓶颈也可能主导运行时间。本章的“段覆盖字节”尤其不能直接当作实际 HBM 流量。它用于提出一个可测量的假设：同一条指令访问的地址更分散，可能需要更多搬运工作。

还有两个边界。第一，某些 lane 被屏蔽时，只对活跃地址求集合；一条只有一个 lane 活跃的指令不必覆盖四个段。第二，改变 lane 与元素的排列顺序但保留地址集合，段数不会改变。合并访问关心这些地址能否归入少量段，并不要求 lane 号一定严格对应递增元素号。更宽的数据类型、跨段访问和其他架构要重新核对访问规则。

## 行与列：转置为什么需要交换工作

设矩阵 $A\in\mathbb R^{R\times C}$ 使用行主序存放，$A_{r,c}$ 的元素偏移是 $rC+c$。如果同一 warp 的 lane 沿列号增长，读取固定的一行，那么相邻地址相差一个元素。若 lane 沿行号增长，读取固定的一列，相邻地址就相差 $C$ 个元素。

例如 $C=32$，读取第 0 行的前 32 个数覆盖 4 段；读取第 0 列的 32 个数，其元素号为 0、32、64、…、992，字节地址间隔 128 字节，每个 lane 落在不同的段。数学上都读取 32 个数，地址集合却完全不同。若行宽不是 8 的倍数，下一行的起点也可能不落在 32-byte 段边界，因此要把行宽和起始位置一起放进地址式。

矩阵转置要求 $B_{c,r}=A_{r,c}$。若每个线程读取一行的一个元素后立即写入对应的转置位置，输入可连续读取，输出却沿着列分散。反过来分配线程，又可能让输出连续而输入分散。一个 block 可以先把输入 tile 连续读入 shared memory，再换一组线程从 shared memory 读取转置位置，最后沿输出的行连续写回。

这不是减少必须读写的矩阵元素，而是让 global memory 两端的访问都采用更合适的布局。shared memory 充当 block 内的数据交换站，因此装载某个值的线程不一定是最终消费它的线程。交换引出了两个新要求：必须保证所有必要的装载先完成，以及共享数组的布局也要适合新的读法。

完整 CUDA 示例采用 $32\times32$ 的数据 tile，启动 `dim3(32, 8)`，共有 256 个线程。每个线程通过 `j = 0, 8, 16, 24` 装载四个元素。这样每个 warp 的 x 维恰好覆盖一行的 32 个位置，同时不用为每个 tile 都启动 1024 个线程。边缘 tile 可能只覆盖部分有效输入，因此每次装载都有边界判断。

## Bank 映射：相同 bank 和相同地址要分开

共享内存由多个存储体（bank）提供并行服务。本节采用 32 个 bank、相邻 32-bit 字映射到相邻 bank 的模型。设 $w$ 为相对某个对齐基址的 32-bit 元素号，则

$$
\operatorname{bank}(w)=w\bmod32.
$$

lane $\ell$ 读取元素 $w=\ell$ 时，32 个 lane 各访问一个 bank。如果都读取元素 $w=32\ell$，它们都映射到 bank 0，却要求 32 个**不同地址**，产生 32 路 bank 冲突的教学例子。反之，32 个 lane 都读取元素 7，是同址读取广播，不是 32 路冲突。

可以用集合避免这个混淆：对每个 bank，收集此次指令要读取的不同元素地址；同一个地址只计一次。某个 bank 的不同地址数决定它需要拆开的服务工作。在这里使用的标量 32-bit 读模型中，各 bank 的最大集合大小给出冲突路数。这个数用于理解地址映射，不是通用的硬件周期预测器。

<BankConflictLab client:visible />

选择“读取 32 列 tile 的一列”：共享数组 `tile[32][32]` 按行排布，固定列 $c$ 的地址为 $w_\ell=32\ell+c$，每个 bank 号都为 $c$。再选择 33 列，地址变成 $w_\ell=33\ell+c$，bank 号为 $(\ell+c)\bmod32$，正好遍历全部 32 个 bank。这个额外列是填充（padding），只改变行跨度，不增加数学上的数据列。

`float tile[32][33]` 分配 4224 字节，比 `float tile[32][32]` 多 128 字节。多用约 3.125% 的共享空间，就改变了列读取的 bank 映射。但不能把“加一列”当作对任意布局的万能优化：元素类型、访问宽度、lane 到索引的映射都可能不同。若原本读取的是连续行，填充并不带来同一种收益；共享空间增加也可能影响驻留 block 数量。

广播的例外针对读取。多个线程向同一地址写不同值不是“自动合并成正确结果”；哪个值最终留下不能用来实现求和。即便是相同 bank 的两个不同地址，bank 冲突通常是性能问题；相同地址的无序读写则可能是正确性问题。讨论前先写明是读还是写、是不是同一地址。

默认选中 tile 内 $(r,c)=(2,5)$。装载线程是 `(tx,ty)=(5,2)`，循环偏移 `j=0`；写回线程则是 `(2,5)`，也是 `j=0`。改变 r 为 18、c 为 27，装载线程变为 `(27,2)`、`j=16`，写回线程变为 `(18,3)`、`j=24`。每个线程沿 y 方向分四轮处理 `ty+j`，因此不能直接把 tile 的 32 行当成 32 个 y 维线程。

无填充时，写回 warp 沿 shared 的固定列读取，元素地址为 $32\ell+c$，全部落在 bank $c$；33 列跨度则变成 $33\ell+c$，32 个 bank 各服务一个不同地址。默认元素的 bank 因而从 5 改成 7；这里改善的是整条 shared 读取指令的映射，而不是改变某个数值或让该元素少经过一层存储。

选择右下 tile，会切到 $35\times67$ 输入中的 block `(2,1)`，只有左上 $3\times3$ 有效。灰色选中位置装载零、参与屏障，输出端跳过写入；有效的 `(2,2)` 对应输入 $A_{34,66}$ 与输出 $B_{66,34}$。此时有效输出列的写回 warp 只有 3 个活跃读取 lane，无填充为 3 路冲突模型，填充后为 1 路；无效输出列不发出 shared 读取。屏障保护所有必要装载完成后才换负责人读取，不能因某线程没有有效输出而跳过协作。图只显示地址布局与责任变化，不把 sector 数或 bank 冲突路数解释成真实 HBM 字节或时间。

## 屏障：给缓冲区安排可证明的阶段

设线程 0 写 `shared[0]`，线程 31 读它。源码里两个线程都执行先写后读，并不意味着线程 31 的读一定晚于线程 0 的写。warp 与 block 的调度不能作为程序顺序保证，我们需要显式的屏障（barrier）。

`__syncthreads()` 是 block 范围的协作屏障；它等待参与的线程到达相应屏障，并保证屏障之前的 shared/global 访问按 CUDA 规定对 block 内其他线程可见。它让我们建立“本轮装载完成，才开始消费”的先写后读关系，不代表整个 grid 的其他 block 已经完成，也不代表 host 已经拿到结果。

<Figure src="gpu/memory-sync.svg" alt="共享缓冲区从装载到发布屏障、消费、回收屏障，再返回下一轮装载" minWidth="40rem">沿箭头看同一 shared 缓冲区的一轮生命周期。发布屏障保护写后读，回收屏障保护上一轮读与下一轮覆盖之间的顺序。</Figure>

为什么有时要两个屏障？想象线程 0 已经读完 tile，立即进入下一轮并覆盖 `tile[0]`，线程 31 却还在读取上一轮 `tile[0]`。第一道屏障只约束“写完才读”，并没有保证“读完才覆盖”。因此在分块矩阵乘等循环中，通常还要在本轮消费完成后放一道屏障。一次性转置没有下一轮共享缓冲区覆盖，所以消费之后不必为回收而再加屏障。

### 边界线程也有协作职责

最危险的写法是把 block 屏障放进按线程索引变化的分支：

```cpp
if (i < n) {
    values[threadIdx.x] = input[i];
    __syncthreads(); // 当同一个 block 中只有部分线程进入时，不能这样用
}
```

CUDA 要求 block 内条件使用屏障时，条件必须使 block 的线程一致到达相应屏障；不能让部分仍参与该 block 工作的线程跳过它。退出线程的规则并不等价于“每个线程可任选是否参加某一道屏障”。本章例子采用更易核对的方法：所有启动线程都走相同屏障序列，无效元素的线程写入中性值。

```cpp
values[threadIdx.x] = i < n ? input[i] : 0.0f;
__syncthreads();
```

求和的中性值是 0，最大值归约常用负无穷，乘积归约则用 1。选择中性值要跟运算对应；把最大值的尾部填成 0，会把全负数组的最大值改错。屏障不能修复算错的填充值，也不能代替数组越界检查。

### Warp、原子和 kernel 边界各解决什么

`__syncwarp(mask)` 的范围是掩码指定的 warp lane，建立参与 lane 之间的同步及内存顺序。掩码指定的未退出线程都必须以相同掩码执行相应调用，调用线程本身也要在集合里；较老架构还有额外的收敛限制。不要先在任意分歧分支里取 `__activemask()`，再假设它代表你希望协作的完整集合。对本章 block 内跨 warp 的 tile 交换，使用 `__syncthreads()` 最直接。

原子操作（atomic operation）解决某个地址上的更新不可被其他更新拆开，例如许多线程向一个计数器执行 `atomicAdd`。它不等于 block 或 grid 屏障，传统原子更新本身也不能被当作其他任意内存访问的发布与获取协议。若线程用一个标志通知数据就绪，需要正确的内存顺序和作用域；普通 `volatile` 标志加自旋不会自动建立这些保证。

对于全 grid 的阶段切换，最容易审查的做法是两个 kernel：第一个生成各 block 的部分结果，第二个读取它们。放在同一个 stream 时，后一个 kernel 按序等待前一个完成；不同 stream 之间需要显式依赖。普通 kernel 不应该让各 block 自旋等待所有其他 block 到达，因为尚未驻留的 block 可能正等待被占用的资源，造成无法前进。合作式启动等专门机制有自己的前提，本章不靠它们完成基础归约。

## 树形归约：把局部结果合并成一行统计

归约（reduction）把多个值合成一个，例如平方和、最大值、指数和。先用 8 个数 $[1,2,3,4,5,6,7,8]$ 手算 block 内树。8 个线程各写一个位置，然后同步；第一层步长 4，前四个位置变成 $[6,8,10,12]$；同步后步长 2，前两个变成 $[16,20]$；再同步后步长 1，位置 0 得到 36。

每一层中，线程 $t$ 读取 $t$ 和 $t+s$，只有 $t<s$ 的线程执行加法。其他线程不加法，但仍到达该层屏障。屏障放在 `if` 外面，让下一层读取到上一层完整的结果。对长度为 $2^k$ 的 block，这棵树执行 $k$ 个合并层，所有层的加法总数仍为 block 大小减一。

完整例子使用 256 个线程：每个线程先通过 grid-stride loop 累加自己负责的输入，在寄存器变量 `sum` 中保留局部结果，再把它写入共享数组 `values[256]`。全体线程同步后，步长依次是 128、64、32、16、8、4、2、1。我们保留每层 block 屏障，避免引入隐含 warp 同步；针对性能的 shuffle 或库归约可以在正确版本上另外比较。

若输入长度为 1003，第一阶段用 4 个 block。前三个各覆盖 256 个输入，最后一个只有 235 个有效位置，余下 21 个线程的私有和为 0，照常写共享数组并参加屏障。第一阶段输出 4 个部分和；第二个 kernel 用一个 block 合并这 4 个数。长度为 0 的输入在 host 上定义结果为 0，并跳过零 block 启动。长度为 1 时，其他线程贡献 0，结果就是那个元素。

在 RMSNorm 中，把输入换成 $x_i^2$，归约后除以元素数得到均方，再计算尺度；在 stable softmax 中，先求一行最大值 $a$，再求 $\sum_i\exp(x_i-a)$。它们需要不同的运算和中性值，但“私有累加、共享合并、明确发布”的结构相似。对于更宽的一行，一个线程还可以读取多个元素，不必让一行长度等于线程数。

### 求和顺序改变了什么

实数加法满足结合律，浮点加法经过逐步舍入，不严格满足它。CPU 从左到右相加，GPU 先算多个局部和再树形合并，可能得到末位不同的结果。不能为了追求逐位一致就直接判定 GPU 结果错误，也不能用“浮点误差”掩盖越界或漏项。

本章 CPU 脚本用 Python 双精度数验证地址与树结构；求和输入采用二进制可精确表示的小数，以便覆盖遗漏能被精确断言发现。CUDA 用 `float32`，一般参考比较应采用同时考虑绝对值和相对值的容差。对于抵消严重的数组，还要考虑数据尺度和累计误差，不能只按最终和大小决定容差。示例的固定小输入适合教学检查，不替代任意数值范围的误差分析。

## 常见误区

- **每个线程读连续数据，就一定合并。** 要看同一条 warp 指令的活跃地址集合，逐线程的连续循环只提供一部分信息。
- **Shared memory 更近，所以多搬一次一定更快。** 装载、屏障和共享空间都有代价；交换布局或多次复用才是搬进去的理由。
- **同一个 bank 就是冲突。** 先区分不同地址与同址读取广播，写入还要单独检查竞态。
- **Warp 总是同步执行，不必写屏障。** 程序不能依赖隐含同步，尤其在独立线程调度下；明确参与集合并使用相应原语。
- **Atomic add 完成就表示所有线程结束。** 地址更新的原子性和参与线程集合的完成是不同保证。
- **多加屏障总能修好。** 屏障的范围必须覆盖真正的生产者与消费者，位置必须让正确的集合到达；block 屏障不能修复跨 block 协议。

## 练习与核对

<details>
<summary>偏移 7 个元素、步长 1 的 warp 覆盖几段？只有前 8 个 lane 活跃时呢？</summary>

完整 warp 访问元素 7 到 38，段号从 0 到 4，共 5 段。前 8 个 lane 访问元素 7 到 14，段号只有 0、1，共 2 段。不要把完整 warp 的结果套给部分活跃集合。
</details>

<details>
<summary>一个 bank 被 32 个 lane 读取，为什么有时是广播，有时是 32 路冲突？</summary>

如果都读元素 7，则请求一个地址，由 bank 7 广播。若读元素 0、32、64、…、992，全部在 bank 0，但有 32 个不同地址，需要拆开服务。判断依据是每个 bank 的不同读取地址集合。
</details>

<details>
<summary>读取 tile 后马上开始下一轮装载，为什么发布屏障还不够？</summary>

发布屏障保证上一轮全部写完才读，不保证全部读完才开始下一轮写。快线程覆盖一个位置时，慢线程可能仍消费旧值。回收屏障将本轮读取与下一轮覆盖分开；若缓冲区只用一次，就没有这个复用危险。
</details>

<details>
<summary>1003 个输入、每块 256 线程，最后一个 block 的无效线程为什么不能随意跳过归约屏障？</summary>

最后一块有 235 个输入和 21 个补零位置。线程的输入是否有效与它在协作树中的职责不同。统一填零并走相同屏障序列，保证树各层读到已发布的值，也让屏障参与集合容易审查。
</details>

<details>
<summary>可以让各 block 写部分和后，自旋等待一个全局计数器到齐吗？</summary>

普通启动无法保证所有 block 同时驻留。已驻留 block 若占住资源等待尚未调度的 block，后者可能永远没有执行机会；此外计数器与数据发布还需要正确内存顺序。本章用同一 stream 的后续 kernel 消费部分和，依赖边界明确。
</details>
