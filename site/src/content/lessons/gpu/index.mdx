把 Python 循环改写成 GPU kernel，先要给每个输出分配线程，确定线程之间的数据依赖。分工正确后，才能测量内存流量和执行时间。

从向量加法开始，thread 负责元素，block 划定协作范围，grid 组织一次启动的工作；warp 与 SM 决定这些工作如何在硬件上推进。CUDA C++ 与 Triton 的写法不同，索引覆盖、同步和结果仍须分别核对。

## GPU 总览：软件分工怎样落到硬件

<Figure src="gpu/overall-model.svg" alt="CPU和主机内存连接GPU，GPU内部多个SM共享L2并访问设备内存；放大SM显示调度、寄存器、执行与shared/L1资源" minWidth="42rem">先沿 CPU 到 GPU 的方向看提交与数据，再从多个 SM 放大到一个 SM。矩形表示概念层次与资源关系，不表示芯片面积、实际单元数量或每次访存的固定路径。</Figure>

从图的最上面开始：应用运行在 CPU，host 代码准备数据并提交 kernel；需要显式搬运时，主机内存与设备内存之间还会发生传输。提交命令与搬运数据是两种操作，不能把 kernel launch 当成一次隐含的全部输入复制。统一内存、集成式设备以及不同互连具有各自的规则，图采用常见的主机/设备概念视图。

再看 GPU 内部：多个 SM 承载 block，多个 SM 可通过共享 L2 与设备内存交换数据。放大一个 SM，线程的局部状态占用寄存器资源，warp 调度器选择能够推进的指令，执行单元完成相应工作。shared memory 提供块内协作的存储，L1 是缓存机制；在许多 NVIDIA 架构中二者共享可配置的物理存储资源，但不能因此混淆用途和同步语义。

最后把软件层放回图中：一次 kernel 的 grid 包含 block，block 包含 thread，块内线性线程号决定 warp 与 lane。grid 的大小来自任务，SM 的数量来自设备。二维或三维 grid/block 是给任务编坐标的方法，不能据此推断 GPU 的执行单元排成同样形状。普通 block 的 shared memory 作用域也不会因为另一个 block 驻留在同一个 SM 就扩大。新架构的 cluster 和分布式 shared memory 属于需要显式使用的额外机制，本图不展开。

沿这张图进入 [G1](/gpu/execution-model/)：先看 block 怎样分批进入 SM，再追踪二维矩阵中的一个元素；用三维切片核对线程编号。到 [G2](/gpu/memory-and-sync/) 时追踪转置数据，到 [G3](/gpu/kernel-design/) 时看共享缓冲区和寄存器的生命周期，最后在 [G4](/gpu/measurement/) 中计算资源上限并测量。

总览依据 [NVIDIA CUDA Programming Model](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)。硬件存储容量、执行单元种类及缓存组织依架构而异；GPC 等层次在图中省略，不能将本图当成某一型号的芯片结构图。

## 四章：先定义工作与依赖，再测量运行

## 阅读路径：从已有知识进入

具备 Python 数组基础就可以从 G1 开始。G3 的矩阵乘需要 [M3 线性代数](/math/linear-algebra/)，softmax 回读 [P3 注意力](/principles/attention/)。不需要先训练完整模型，才能理解线程索引与内存地址。

本路线位于推理系统之前：G3 定义算术强度与屋顶线，G4 定义测量边界，[S2 单卡上限](/systems/accelerator/) 再代入真实硬件规格，[S3 FlashAttention](/systems/flash-attention/) 应用分块与融合减少注意力的中间流量。已经读过 [S1 计算账本](/systems/ledger/) 的读者，可以把那里的负载强度带到 G3 的屋顶线上对照。

需要解释框架怎样生成与融合 kernel 时，结合 [F7 torch.compile](/frameworks/torch-compile/) 的 Dynamo、AOTAutograd 与 Inductor 管线。需要解释 CUDA Graph 与发射开销时，读完 G4 再回 [S6 GPU 执行器](/systems/engine-execution/)。跨设备并行属于 [S9 集群](/systems/cluster/)；block、warp 是一张 GPU 内的工作组织，不要与 tensor parallel rank 混成一层。

## 代码与图：三种证据各自有边界

交互 SVG 显示一维到三维索引、warp 布局、block 调度、地址段、bank、转置路径、tile 生命周期、驻留资源和 stream 依赖。数字来自可手算的模型，颜色显示任务、地址或阶段关系。图片由实际地址表或小矩阵生成，静态结构图说明数据与执行阶段；它们不提供某张显卡的实测吞吐。

每章都有 CPU 验证脚本，检查索引覆盖、访存段数、归约、分块矩阵乘与资源账。它们证明教学算法或计数关系，不模拟 GPU 的全部调度、缓存与指令执行。

`code/gpu/examples/` 另外提供完整 CUDA C++ 和 Triton 示例，章节中说明编译、运行与边界。真实 GPU 程序需要相应设备、驱动与工具；CPU CI 不运行它们。G4 的 event 脚本会在真实设备上记录版本与时间，资料中的工具命令帮助核对越界、同步和执行瓶颈。

## 心智模型：始终带着六个问题读代码

1. 每个输出的负责人是谁？改变 launch 配置后是否仍然没有漏写与重复写？
2. 一个 block 内哪些线程协作？一个 warp 内哪些 lane 在当前路径上有效？
3. 这条指令到底访问哪些地址？地址连续、对齐与数据复用分别改变什么？
4. 谁生产、谁消费？同步保证的是哪些参与者和哪段内存的顺序？
5. 哪种资源限制驻留？更多线程是否真的增加可执行的独立工作？
6. 计时区间包含什么？结果已核对吗，所报字节是逻辑请求还是物理流量？

从 [G1 执行模型](/gpu/execution-model/) 开始，用一百个元素写清楚第一份分工。
