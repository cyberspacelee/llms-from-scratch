把一段 Python 循环交给 GPU，并不是把每次迭代随意丢给一个“核心”。你要先决定每个输出由谁负责，哪些线程会读彼此的结果，哪些操作可以重叠。做到这些以后，再讨论内存流量和执行时间，才有可以检验的优化。

本路线从向量加法进入编程模型。thread 有自己的执行状态，block 确定协作范围，grid 组织一次启动的工作；warp 与 SM 解释这份工作如何在有限硬件上推进。CUDA C++ 把线程职责写明白，Triton 把一段数据的计算写在一起，两种视角最终都要回答同样的正确性问题。

## 四章：先定义工作与依赖，再测量运行

| 章 | 核心问题 | 读完能核对的结果 |
| --- | --- | --- |
| G1 | 一个函数怎样覆盖整个数组 | 100 个元素、64 线程一块，共 2 块和 28 个尾部位置 |
| G2 | 相同计算为什么搬运不同数量的数据 | 对齐的 32 个 float32 覆盖 4 个 32-byte 段；偏移一元素覆盖 5 段 |
| G3 | 怎样从算对走到分块与融合 | 非整除的小矩阵乘输出相同，协作装载与边界补零可逐项核对 |
| G4 | 怎样解释并测量资源、依赖与时间 | 教学 SM 的驻留限制，跨 stream 的 event 顺序，完整测量区间 |

这里的 warp 宽度、bank 例子和 CUDA 接口以 NVIDIA 为对象。访问另一厂商的 GPU 时，应核对该平台的执行组宽度、同步与内存规则，不把本路线的常数照搬过去。

## 阅读路径：从已有知识进入

具备 Python 数组基础就可以从 G1 开始。G3 的矩阵乘需要 [M3 线性代数](/math/linear-algebra/)，softmax 回读 [P3 注意力](/principles/attention/)。不需要先训练完整模型，才能理解线程索引与内存地址。

如果从系统路线进入，建议 [S2 单卡上限](/systems/accelerator/) → G1–G3 → [S3 FlashAttention](/systems/flash-attention/)。S2 负责算术强度和屋顶线，G 路线负责把算子映射到线程、协作与存储，S3 再应用这些思想减少注意力的中间流量。

需要解释 CUDA Graph 与发射开销时，读完 G4 再回 [S6 GPU 执行器](/systems/engine-execution/)。跨设备并行属于 [S9 集群](/systems/cluster/)；block、warp 是一张 GPU 内的工作组织，不要与 tensor parallel rank 混成一层。

## 代码与图：三种证据各自有边界

七个交互 SVG 显示索引、lane、地址段、bank、tile、驻留资源和 stream 依赖。数字来自可手算的模型，颜色显示任务或地址关系。图片由实际地址表或小矩阵生成，静态结构图说明数据与执行阶段；它们不提供某张显卡的实测吞吐。

每章都有 CPU 验证脚本，检查索引覆盖、访存段数、归约、分块矩阵乘与资源账。它们证明教学算法或计数关系，不模拟 GPU 的全部调度、缓存与指令执行。

`code/gpu/examples/` 另外提供完整 CUDA C++ 和 Triton 示例，章节中说明编译、运行与边界。真实 GPU 程序需要相应设备、驱动与工具；CPU CI 不运行它们。G4 的 event 脚本会在真实设备上记录版本与时间，资料中的工具命令帮助核对越界、同步和执行瓶颈。

## 心智模型：始终带着六个问题读代码

1. 每个输出的负责人是谁？改变 launch 配置后是否仍然没有漏写与重复写？
2. 一个 block 内哪些线程协作？一个 warp 内哪些 lane 在当前路径上有效？
3. 这条指令到底访问哪些地址？地址连续、对齐与数据复用分别改变什么？
4. 谁生产、谁消费？同步保证的是哪些参与者和哪段内存的顺序？
5. 哪种资源限制驻留？更多线程是否真的增加可执行的独立工作？
6. 计时区间包含什么？结果已核对吗，所报字节是逻辑请求还是物理流量？

从 [G1 执行模型](/gpu/execution-model/) 开始，用一百个元素写清楚第一份分工。
