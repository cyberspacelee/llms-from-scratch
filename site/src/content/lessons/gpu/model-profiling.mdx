[G4](/gpu/measurement/) 比较的是同一个 GEMM 的 tile。本实践固定完整 Decoder 的参数，改变注意力执行后端。目标是先证明这份输入上的输出与参数梯度一致，再观察一次完整前向包含哪些算子。

## 固定模型、输入与核对边界

实验用统一包的两层现代 Decoder，$B=2,T=32,D=32,D_{ff}=64,V=64$，固定随机种子 61，关闭训练随机性。将模型复制成两份，分别用显式 attention 与 PyTorch SDPA；对 logits 的平方均值求导，逐个比较所有参数的梯度。

CPU 使用 float64、容差 $10^{-10}$，CUDA 使用 float32、容差 $2\times10^{-5}$。复制的是同一权重，不能分别初始化两个模型后比较，也不能把输出一致当作梯度一致。此核对不是语言模型训练质量评估。

## CPU 先验证与看轨迹

```sh
uv run python -m examples.gpu.model_profile --trace /tmp/model-cpu-trace.json
```

脚本首先核对两后端，然后在 `no_grad` 下预热，各采集一次带 `modern_lm_manual`、`modern_lm_sdpa` 标签的前向，打印按 CPU self time 排序的统计表，选填参数导出 Chrome trace。这里没有 optimizer update；梯度核对位于采集区间之外。

打开 trace 时先找整次前向的标签范围，再看 normalization、投影、attention、FFN 各项时间。多个算子有依赖和嵌套，不能将各级总时间直接相加。某个算子数量变少也不能独自证明完整模型更快。

## CUDA 使用独立 GPU 环境

仓库锁定入口优先 CPU PyTorch。按 README 创建与驱动匹配的独立 GPU 环境，避免 `uv run` 把已安装的 CUDA 构建覆盖成 CPU 构建：

```sh
uv venv .venv-gpu
uv pip install --python .venv-gpu/bin/python -e '.[gpu]'
.venv-gpu/bin/python -m examples.gpu.model_profile --device cuda --trace /tmp/model-cuda-trace.json
```

运行前核对 [PyTorch 官方安装选择](https://pytorch.org/get-started/locally/)中的构建和设备条件。CUDA 路径在 CPU activity 外增加 CUDA activity，另对每个后端连续执行 30 次前向，用 event 总时间除以 30 报均值，并报告相对起点的峰值分配增量。这是固定形状的小型探针，没有报告独立样本中位数；若要作性能结论，按 G4 补足样本波动、顺序反转和端到端边界。

当前无 CUDA 环境，设备正确性和 GPU 耗时未实测。CPU manual/SDPA 结果不保证选到哪一个 CUDA 后端；SDPA 的实际 kernel 随 dtype、shape、mask 和设备改变。即使看到融合 attention，也不能把完整前向耗时全部归给它。

## 练习与核对

<details>
<summary>两后端 logits 一致，但某个参数梯度有差异，可以直接继续比性能吗？</summary>

应先定位梯度差异：检查相同权重、目标、mask、dropout、dtype 和容差。性能比较必须使用符合任务数值契约的实现；输出通过不能覆盖反向错误。
</details>

<details>
<summary>profiler 中 SDPA 使用一个融合 kernel，是否证明它比显式版本更快？</summary>

不证明。融合会改变临时数据与发射路径，实际时间还受形状、资源、其余算子和采集干扰影响。先用 trace 定位候选瓶颈，再退出 profiler 按同一计时协议复测。
</details>

执行后端条件见 [PyTorch SDPA](https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention.html)，采集接口见 [PyTorch Profiler](https://docs.pytorch.org/docs/stable/profiler.html)。
