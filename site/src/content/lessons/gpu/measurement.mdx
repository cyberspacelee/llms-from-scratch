你已经在 [G1](/gpu/execution-model/) 把数组分给线程，在 [G2](/gpu/memory-and-sync/) 建立共享数据的同步边界，在 [G3](/gpu/kernel-design/) 把小矩阵乘写成分块计算。现在有两个都算对的版本：一个使用更大的 tile，另一个启动更多 block。该保留哪个？仅看代码里的线程数无法回答；更大 tile 可能减少搬运，也可能占用更多寄存器，使 SM 上能同时等待和执行的 warp 变少。

本章把这个问题拆成三个可以核对的层次。第一层是资源：哪些线程已经驻留、哪些指令具备执行条件。第二层是依赖：哪些操作允许重叠、哪些操作必须等待。第三层才是测量：记录的时间包住了哪段工作，工具观察是否改变了运行。每一层都能帮你提出假设，但最终选择实现需要真实 GPU 数据。

这里的驻留与时间线实验是可手算的教学模型。它们没有调用你的显卡，也不会根据动画给出某款设备的吞吐。配套 CPU 脚本核对模型算术；可选 GPU 脚本才记录 CUDA event 时间。屋顶线的定义和硬件产品数字回读 [S2 单卡的上限](/systems/accelerator/)，本章讨论怎样把一次实际运行与那些上限比较。

## 延迟与吞吐：等待时还可以让谁执行

延迟（latency）是某一次操作从开始到完成的时间。吞吐（throughput）是单位时间完成的操作或处理的数据量。读一个不在缓存中的值可能要等一段时间；有很多可运行的 warp 时，SM 可以在一个 warp 等待期间发射其他 warp 的指令。这样增加了整体完成工作的密度，但那个读请求本身没有因为换了 warp 就瞬间完成。

设一个教学任务先等 4 个逻辑时间单位，再做 1 个单位的计算。只有一个任务时，完成一次需要 5 单位。若两个任务的等待相互独立，且执行资源允许，可以先让两者都发起等待，再依次执行它们的计算。两个任务的总完成时间可能接近 6，而不是 10。这只是说明重叠如何减少空档；真实延迟、发射宽度和指令依赖需要硬件与工具报告，不能直接套这两个数字。

关键条件是“有其他可运行的工作”。如果后面的指令都依赖刚才的读结果，继续排同一条依赖链不会隐藏等待。同一线程中相互独立的计算提供指令级并行（instruction-level parallelism，ILP）；其他线程或 warp 提供线程级并行。两者都可能减少执行单元空闲，也都可能需要更多寄存器保存中间值。

因此，第一张心智图不是“把更多线程塞进 GPU 就更快”，而是先把线程状态分开：尚未调度的 block 在等待资源；已驻留的 warp 已拥有执行上下文；这些 warp 中又只有一部分具备发射下一条指令的条件。一个 warp 驻留但等待内存时，不能把它当作正在做算术。多个 warp 都在等待同一个瓶颈时，增加数量也不保证增加有效吞吐。

CUDA 的具体 warp 调度、寄存器与共享内存资源随架构变化，定义见 [Advanced Kernel Programming](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)。程序不能依赖某个 warp 一定先执行。优化可以利用独立工作增加选择机会；正确性仍然由 [G2](/gpu/memory-and-sync/) 的同步与内存访问规则建立。

## 驻留资源：先算一个 SM 装得下多少 block

占用率（occupancy）通常讨论一个 SM 的活跃 warp 数占最大可驻留 warp 数的比例。这里“活跃”指已经驻留的 warp；它不表示每个周期所有 lane 都在执行，也不等于整张 GPU 的计算单元利用率。理论 occupancy 由资源配置给出，实际运行中采样得到的 achieved occupancy 还受 block 数、尾部工作和任务分布影响。

先做一个刻意简化的资源账。假设某个教学 SM 可驻留 64 个 warp，拥有 65,536 个 32-bit 寄存器和 96 KiB shared memory，block 数上限为 32。这些是用来手算的参数，不是本章推荐显卡的规格。设一个 block 有 $n_{\mathrm{th}}$ 个线程，每线程使用 $r$ 个寄存器，每块 shared memory 使用 $s$ 字节。

每块所需的 warp 数为

$$
w=\left\lceil\frac{n_{\mathrm{th}}}{32}\right\rceil.
$$

末尾不完整 warp 仍占一个 warp 的分组。为了让接下来的账容易看清，先取 $n_{\mathrm{th}}=256$，所以 $w=8$。每线程 32 个寄存器意味着每块需要 $256\times32=8192$ 个寄存器。每块再用 16 KiB shared memory。

四条限制分别给出：warp 容量允许 $64/8=8$ 块，寄存器允许 $65536/8192=8$ 块，shared memory 允许 $96/16=6$ 块，block 数允许 32 块。一个 block 同时消耗这些资源，因此能驻留的块数取最小值，得到 6。对应 48 个 warp，教学模型的理论 occupancy 是 $48/64=75\%$。

<KeyEq label="教学资源上界">

$$
\begin{aligned}
k&=\min\left(
 \left\lfloor\frac{W_{\max}}w\right\rfloor,
 \left\lfloor\frac{R}{n_{\mathrm{th}}r}\right\rfloor,
 \left\lfloor\frac{S}s\right\rfloor,
 K_{\max}\right),\\
\rho&=\frac{kw}{W_{\max}}.
\end{aligned}
$$

</KeyEq>

其中 $W_{\max}$、$R$、$S$、$K_{\max}$ 分别是 SM 的 warp、寄存器、shared memory 和 block 容量；$k$ 是驻留块数，$\rho$ 是比例。若 $s=0$，shared memory 不提供限制，不做除零；本章程序用 block 上限代替这一项。若某项连一块都容不下，模型给出零，这时配置不能依靠“多等一下”获得空间。

<OccupancyLab client:visible />

将每块 shared memory 从 16 KiB 改为 32 KiB，另外三条限制不变，shared memory 只容得下 3 块，于是 occupancy 降到 $24/64=37.5\%$。将它恢复到 16 KiB，再把每线程寄存器改成 64，寄存器限制变成 4 块，得到 50%。这些变化不是优化好坏的结论，而是在解释哪个资源先到上限。

### 简单除法在哪些地方需要修正

实际 GPU 不是按任意一个寄存器、任意一个字节精确分配资源。寄存器和 shared memory 有分配粒度，线程块还有单块线程数、单块资源量及配置限制。编译器报告的寄存器使用量和程序申请的 shared memory 也可能与纸面变量数不同。我们的交互没有模拟这些架构细节，因此它是上界关系的教学模型，不能替代 CUDA occupancy API。

在 GPU 上，应结合设备属性、编译器资源报告和 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 核对指定 kernel 的驻留数量，再看 Nsight Compute 的实际指标。最大线程数与 warp 容量之间的关系也应从该设备得到，而不是把上面的 64 当作通用常数。详细差异见 [CUDA Best Practices 的 occupancy 讨论](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#occupancy)。

另外，即使一个 SM 理论上能容纳 6 块，整个 grid 只有 2 块，也不可能让很多 SM 同时忙起来。任务数量、尾部块的完成时间和负载均衡是另一层限制。假设八个 SM 都在执行，有的 block 很快完成、有的很慢，最后一段运行可能只剩一小部分 SM 工作。平均指标会把这个尾部阶段计进去，而 launch 配置本身没有变化。

### 更高 occupancy 为什么可能更慢

如果强制每线程少用寄存器，编译器可能把中间值 spill 到线程私有的 local memory，增加存取。一个保留更多寄存器的版本虽然同时驻留的 warp 少一些，却可能减少这种搬运。更大的 tile 同样可能增加 shared memory 使用、降低驻留，同时提高数据复用。是否值得，要同时看等待是否被隐藏、流量是否下降和实际时间是否缩短。

因此，本章不把 occupancy 设成越大越好的优化分数。把 75% 变成 100% 只说明多驻留了一些 warp，不能直接推导吞吐增加三分之一。若已经受算术管线或内存带宽限制，多出的 warp 可能不能增加供给；若它们补上了等待空档，就可能有帮助。读报告时应把 occupancy 与可发射 warp、访存及运行时间一起解释。

## Stream 与 event：把允许的顺序写出来

CUDA stream 可以理解为设备操作的有序队列。同一个 stream 里先提交 A 再提交 C，C 会在 A 之后执行。CPU 可以在提交后继续工作；这种 host/device 异步与队列内部的执行顺序不是矛盾。不同 stream 之间则不能仅根据 CPU 的调用顺序假设依赖，除非相关 API 的特定同步语义提供了保证。

考虑三个 kernel。A 生成一份 C 要读取的数据；B 使用另一份数组，与 A 无数据关系；C 消费 A 的结果，也排在 B 之后。我们希望 B 可以与 A 重叠，同时保证 C 不抢先读取。

若都放一个 stream，A、B、C 依次执行，依赖正确，但没有利用 B 的独立性。若把 A 放 stream 0，B、C 放 stream 1，B 可以独立推进，然而 stream 1 不会自动知道 C 的输入来自 A。应在 A 后记录一个 event，再让 stream 1 在 C 前等待该 event。这是在设备队列之间建立顺序，CPU 不必为这条依赖等待整个 GPU。

<StreamTimelineLab client:visible />

用逻辑时长 A=5、B=3、C=2 手算。同一队列的总时长是 10。在允许 A 与 B 重叠、并建立 event 依赖的模型里，B 在 3 完成，A 在 5 完成，C 从 5 执行到 7。去掉 event，C 会在 B 后于 3 开始，发生提前读。图里更短的“5”不是一个可接受的优化结果：它属于缺少依赖的程序。

把 A 改成 3、B 改成 5 后，没有 event 的模型里 C 恰好从 5 开始，看起来没有提前读取。这个程序仍未建立依赖。换一张 GPU、改变输入大小，或 B 的耗时变短，就可能暴露问题。正确性不能建立在两段工作的偶然耗时关系上。

### 两个 stream 也不承诺同时执行

运行时还要判断资源是否允许重叠。某个 kernel 若占满所需执行资源，另一个 kernel 可能等它结束；独立 kernel 也可能争用同一条带宽。拷贝与计算重叠还受设备能力、传输方向、缓冲区和同步条件影响。涉及主机缓冲区的异步传输通常要考虑 page-locked 内存；换用 pinned memory 同样不保证所有情形都有收益。

默认 stream 还存在 legacy 与 per-thread 两种语义；普通 stream 与 non-blocking stream 的交互也有具体规则。初学时可以为实验显式创建 stream，并使用 event 表达数据依赖，再回官方文档理解默认流。不要把不同 stream 当成不同显卡，也不要假定一个 stream 独占一个 SM。定义与边界见 [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)。

在 PyTorch 中管理 stream 时，执行依赖和张量存储生命周期又是两个问题。除了让消费者等待生产完成，还要保证内存不会被 allocator 在另一 stream 仍使用时复用。实际框架代码应按其 stream 与 allocator 接口建立正确的使用契约；把一个 C++ event 例子机械翻成几个 Python 调用，并不能自动处理所有对象生命周期。

## 测量边界：提交时间、GPU 时间与应用时间

下面这段 Python 代码为何可能得到非常小的数字？

```python
start = time.perf_counter()
result = gpu_operation(x)
elapsed = time.perf_counter() - start
```

如果 `gpu_operation` 只完成提交，CPU 在 GPU 计算完成前就读了结束时刻。这段代码测到的主要是主机调用与发射开销，并没有测到结果可用的延迟。在调用前插入一次同步，也只能排除已有工作，不能使后面的异步调用自动变成完成等待。

一个可信报告应先写测量问题。只关心 kernel 在 GPU 上的区间，可以用同一 stream 上的两个带计时 event 包围它，等待结束 event 完成，再读取时间差。若关心用户等待结果的时间，要让 CPU 计时包含所需传输、提交、计算和结果等待。若关心一轮服务请求，还应包含调度、排队、采样与协议开销，回读 [S10 服务评估](/systems/serving-evaluation/)。

<Figure src="gpu/measurement-boundaries.svg" alt="CPU 提交、H2D 与 D2H 传输、kernel 以及 event 区间的边界">横向位置表示不同阶段的先后，长度只示意。event 包围 kernel；CPU 端到端计时应从输入所需操作开始，到结果可以安全使用时结束。</Figure>

一个 event 是插入队列的标记，不是 CPU 调用 `record` 时立即读取的设备时钟。它在设备队列运行到该位置时生效。因此记录结束 event 后必须等它完成，才有完整区间。跨 stream 测量还需要建立事件依赖；两个没有顺序关系的标记不能随意相减后当成一个 kernel 的耗时。

即使标记放得正确，短 kernel 也可能受到发射间隙、event 开销和其他任务的干扰。GPU 很快执行了开始标记，但下一项工作尚未提交，区间里可能出现空档。测量不是只调用一个 API 就结束的事情：重复、预热、隔离干扰和固定区间都是为了让数字回答同一个问题。

### 预热与重复：先排除一次性的工作

第一次调用可能包含 CUDA 上下文初始化、内存分配、JIT 编译、库的算法选择或缓存准备。把它和稳定执行混在一起，会把“启动一套程序的代价”与“重复一个算子的代价”混成一个数字。两者都可能值得测量，但要分开报告。使用 Triton 时尤其要交代编译与 autotune 是否纳入时间。

本章的 GPU 示例预先分配输入与输出，执行若干次预热，同步清空已有工作，再为重复加法记录 event。这样回答的是“重复使用已有数组进行向量加法”的区间，不包括 CPU 到 GPU 的数据准备。它另外用 CPU 时钟记录整批提交加最终等待，让你看到设备区间与主机端区间不能简单互换。

除了中位数，脚本输出最小与最大区间。中位数用于减少偶然波动影响，最小值和最大值帮助发现干扰；它们不代替样本分布分析。不同版本比较时，元素数、dtype、stride、预热次数和重复次数应一致。比较小 kernel 时也可以测一批工作总区间，但要说明除以次数得到的是该运行方式下的平均，不能偷偷把批量发射改成每次同步。

### 有效带宽：先定义你数了哪些字节

若向量加法每个元素读两个 float32、写一个 float32，逻辑读写量是每元素 12 字节。用元素数 $N$ 和所测区间 $t$ 秒，定义有效带宽为

$$
\mathrm{BW}_{\mathrm{eff}}=\frac{12N}{t\times10^9}\quad\mathrm{GB/s}.
$$

这是一种按算法必须读写的字节计算的速率。它不等于测量了 HBM 物理流量：同一数组反复执行可能命中缓存，实际内存系统也可能搬运未被使用的字节。对于分块与融合，要重新说明逻辑字节怎么数；不能将寄存器复用的每次乘加都当成重新读 HBM。

举一个纯算术核对：若有一百万个元素，逻辑读写量是 12 MB，假设某条记录给出 0.1 ms，则有效带宽为 120 GB/s。这里的 0.1 ms 是演示单位换算的假设，并非本机实测。实际运行脚本才会输出真实时间。GB 使用 $10^9$ 字节，GiB 使用 $2^{30}$ 字节，与规格比较时保持同一单位。

## 从错误检查到 profiler：工具分别回答什么

先检查输入输出。越界读写、未初始化数据或同步错误产生的快速结果没有比较意义；某次测试没崩溃也不是没有错误的证明。对 [G3 的示例](/gpu/kernel-design/) 应使用非整除维度、已知小矩阵与参考实现，先核对所有输出，再运行错误检查工具。

[Compute Sanitizer](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html) 提供不同检查器。memcheck 关注内存访问错误；racecheck 检测 shared memory 相关数据竞争危险；initcheck 检测未初始化 global memory 的使用；synccheck 检查同步原语的用法。它们的范围不同，racecheck 不能作为排除了所有跨 block/global memory 竞争的证明。

例如，在有 CUDA 环境时对 G3 的可执行文件执行：

```sh
compute-sanitizer --tool memcheck ./tiled_gemm
compute-sanitizer --tool racecheck ./tiled_gemm
compute-sanitizer --tool initcheck ./tiled_gemm
compute-sanitizer --tool synccheck ./tiled_gemm
```

这些命令会改变运行开销。Sanitizer 下的时间用于定位错误，不用来报告正常吞吐。没有报告也只覆盖已执行的输入、路径与工具检测范围，所以还要保留数值对照与边界测试。

### 先看整条时间线，再看单个 kernel

[Nsight Systems](https://docs.nvidia.com/nsight-systems/UserGuide/index.html) 帮你观察 CPU、CUDA 调用、kernel、拷贝和相关事件在时间线上如何排列。若主要空档发生在两次 kernel 之间，先检查主机发射、同步与输入准备；如果 kernel 一直在跑却很慢，再进入 kernel 内部分析。NVTX 可以标记有意义的阶段，但不要为了看清一张图把计时区间本身改变。

[Nsight Compute](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html) 进一步观察一个 kernel 的执行资源和内存行为。阅读指标前写下问题，例如“这个 tiled 版本减少了请求字节，为什么时间没有下降？”随后查看寄存器、shared memory、驻留与访存证据，而不是寻找一个看起来漂亮的百分比。

```sh
nsys profile --trace=cuda,nvtx -o gemm-timeline ./tiled_gemm
ncu --set basic ./tiled_gemm
```

工具可能需要系统权限或配置支持，命令选项与指标名也可能随安装版本变化，运行前先用相应 `--help` 核对。保存输入、命令、设备名称、驱动、CUDA/框架版本与原始报告。报告截图应来自真实采集，不能用教学时间线代替。仅对一个微小示例采集报告，也不能代表生产推理引擎的并发行为。

### 观测本身会改变运行

Nsight Compute 为收集多组计数器可能重放 kernel 或应用，并保存、恢复相关内存状态。缓存控制、重放方式与并发环境会影响观测。profiler 运行的整个墙钟时间因此不能替代不带工具的端到端延迟。某个指标要解释的区间与实际计时要比较的区间，应在报告中分别说明。

优化时每次改变一个能解释的因素。固定其他条件后扩大 tile，先确认结果一致，再核对逻辑搬运和资源使用，最后比较重复测量。若改了输入布局、精度和 launch 配置三件事，即使快了，也很难确定收益来自哪里。性能反例同样有价值：它能让你修正“更大 tile 一定更快”这类未经检验的判断。

## 配套代码：模型核对与真实计时分开运行

CPU 脚本只依赖标准库：

## 常见误区：把一个指标当成所有答案

- **Occupancy 是 GPU 利用率。** 它描述驻留 warp 的比例，不直接描述计算管线每个周期完成了多少工作。
- **每线程少用寄存器一定更快。** 资源占用可能下降，也可能产生更多 spill 或减少有用的 ILP，需要看整个实现。
- **两个 stream 就有两倍速度。** 依赖、硬件资源与竞争限制重叠，程序首先要建立正确顺序。
- **开始前同步一次就够了。** 异步工作之后还必须等待结果或结束 event，否则计时边界仍不完整。
- **Event 时间就是用户等待时间。** 它只描述标记之间的设备区间；传输、调度和服务协议可能在区间之外。
- **有效带宽比 HBM 规格高就是测量错误。** 若算法重复访问缓存，逻辑字节速率与物理 HBM 流量并非同一个量，先检查口径。

## 练习与核对

<details>
<summary>每块 256 线程、每线程 32 个寄存器、每块 32 KiB shared memory，教学 SM 的 occupancy 是多少？</summary>

每块 8 个 warp，warp 与寄存器各允许 8 块，shared memory 只允许 $96/32=3$ 块，block 上限允许 32 块。取最小值 3，于是活跃 warp 数为 24，occupancy 为 $24/64=37.5\%$。这只是教学资源账，真实硬件还要计分配粒度与配置限制。

</details>

<details>
<summary>A 用 3 单位、B 用 5 单位，没有 event 时 C 恰好在 A 完成后开始，能删除依赖吗？</summary>

不能。模型里的时长只描述这组参数，而没有 event 的程序缺少生产与消费之间的顺序保证。改用 A=5、B=3 就能得到 C 提前读的反例。应把 event 作为数据依赖，而不是作为某组时长下避免冲突的补丁。

</details>

<details>
<summary>两百万个 float32 元素做向量加法，假设完整区间为 0.2 ms，有效带宽是多少？</summary>

读两份输入、写一份输出，逻辑字节为 $2000000\times4\times3=24000000$。除以 $0.0002$ 秒和 $10^9$，得到 120 GB/s。这个假设区间只能核对算术，不提供物理 HBM 流量或某张 GPU 的性能证据。

</details>

<details>
<summary>CPU 调用耗时 0.01 ms，event 区间 0.5 ms，哪一个是算子的耗时？</summary>

先定义问题。CPU 调用若没有最终等待，0.01 ms 主要是提交时间。event 区间如果正确建立顺序并完成等待，0.5 ms 描述该设备区间。如果用户输入仍在 CPU、结果也要返回 CPU，还要把传输等阶段计入端到端时间，两者都不能直接替代它。

</details>

<details>
<summary>提高理论 occupancy 后实际时间变长，下一步看什么？</summary>

确认结果与测量边界一致，然后查看寄存器使用和 spill、shared memory 与访存行为、可运行 warp 和实际驻留。检查是否为提高驻留牺牲了 tile 复用或 ILP，以及工作规模是否足够。提出一个具体解释后，只改变相关因素重新测量，不能仅凭 occupancy 的百分比否定运行结果。

</details>

带着这些边界回读 [S2](/systems/accelerator/) 的硬件上限，再进入 [S3 FlashAttention](/systems/flash-attention/) 与 [S6 GPU 执行器](/systems/engine-execution/)：前者减少注意力的中间流量，后者用 CUDA Graph 减少重复发射开销，它们都仍需满足资源、依赖和正确性约束。
