[G3](/gpu/kernel-design/) 用共享内存分块计算 $C=AB$。它证明了分块能复用输入，却没有证明 tile 越大越快。本章始终比较**同一个**连续 float32 矩阵乘：A、B、C 都是 $1024\times1024$，先考虑 G3 CUDA kernel 的 $t=16$，再考虑只改变 tile 边长的 $t=32$ 候选。仓库的 CUDA 示例只实现并验证了 $t=16$，下文对 $t=32$ 的资源分析是待设备实验检验的预测。两者必须输出同一个 C，使用同一设备、编译选项和计时区间。没有 GPU 时，我们只核对资源与依赖的教学模型，不给出虚构的加速比。

先修是 [G1 的 block/warp](/gpu/execution-model/)、[G2 的 shared memory 与屏障](/gpu/memory-and-sync/) 和 [G3 的 tile](/gpu/kernel-design/#一个-tile-怎样累计沿-k-分段复用输入)。读完后，应能解释：大 tile 少搬了哪些逻辑数据，又多占了哪些资源；两个 kernel 能否并发；一个时间数字究竟包住了哪些工作。

## 从 G3 的 tile 得到一个待检验的假设

G3 的教学映射让一个 thread 累计一个输出。每次沿 K 前进 $t$，一个 block 读 A、B 各 $t^2$ 个 float32，在这些值上做约 $t^3$ 次乘加。只算输入读取，局部算术强度为 $2t^3/(2t^2\cdot4)=t/4$ FLOP/byte。$t=16$ 是 4，$t=32$ 是 8。后者让一份输入在 block 内服务更多乘加，所以有理由试它。

但这个比值不计输出、边缘补零、跨 block 的缓存复用，也不是 HBM 计数器读数。对本例，两个版本的数学运算量同为 $2MNK=2\cdot1024^3\approx2.15$ GFLOP。若只按每个 block 从 global memory 请求的输入元素计，且忽略缓存命中，$t=16$ 约请求 $2MNK/t=134{,}217{,}728$ 个 float32，$t=32$ 约为其一半；两个版本都另外写 $MN$ 个 C 元素。相邻 block 可能从 L2 取得数据，所以这些请求数不能直接当成 HBM 字节或预言运行时间。G3 的[屋顶线](/gpu/kernel-design/#屋顶线强度决定上限贴着哪条线)也只是上界。

这就留下可证伪的问题：**减少请求是否抵过更大 block 的资源代价？** 先算驻留，再在设备上测同一个工作负载。

## 驻留资源：先算一个 SM 装得下多少 block

Occupancy 指一个 SM 中**已驻留 warp 数**占可驻留 warp 上限的比例。驻留意味着执行上下文已分配，不意味着该 warp 此刻正在发射指令；GPU utilization、算力达成率和 kernel 耗时也不是这个比例。一个 warp 等待内存时，另一个可运行 warp 可能填补空档，因此驻留资源值得算，但它不是优化目标本身。

用一台**假想** SM 手算：最多 64 个 warp、65,536 个寄存器、96 KiB shared memory、32 个 block。假定两个版本编译后都使用每 thread 32 个寄存器。G3 的两份 float32 输入 tile 共占每 block $8t^2$ 字节。

| 资源账 | $t=16$ | $t=32$ |
| --- | ---: | ---: |
| Threads / warps per block | 256 / 8 | 1024 / 32 |
| Registers per block，按假设 | 8192 | 32768 |
| Shared memory per block | 2 KiB | 8 KiB |
| Warp 上限允许的 block | 8 | 2 |
| 寄存器上限允许的 block | 8 | 2 |
| Shared 上限允许的 block | 48 | 12 |
| 最终驻留 block / warp | 8 / 64 | 2 / 64 |

同样是理论 occupancy 100%，大 tile 每 SM 却只有两个独立 block；若 grid 很小或某块结束较晚，尾部工作可能让更多 SM 空闲。若 $t=32$ 的实际编译结果是每 thread 64 个寄存器，寄存器上限就只容一个 block，理论 occupancy 降至 50%。降低寄存器数可能引入 spill 到 local memory；这些情况都不能从源码中一个累计变量的数量推断。

<KeyEq label="教学资源账">
$$
k=\min\!\left(
\left\lfloor\frac{W_{\max}}{\lceil n_{\mathrm{th}}/32\rceil}\right\rfloor,
\left\lfloor\frac{R}{n_{\mathrm{th}}r}\right\rfloor,
\left\lfloor\frac{S}{s}\right\rfloor,
K_{\max}\right),
\qquad
\rho=\frac{k\lceil n_{\mathrm{th}}/32\rceil}{W_{\max}}.
$$
</KeyEq>

这里 $n_{\mathrm{th}}$ 是每块 thread 数，$r$ 是每 thread 寄存器数，$s$ 是每块 shared 字节；$W_{\max},R,S,K_{\max}$ 是四种 SM 容量。若 $s=0$，跳过那项除法。某项小于一块时，配置不能驻留。公式只展示约束怎样相交；真实设备还按粒度分配资源，并限制单块 thread、寄存器和 shared 大小。特别是 1024-thread block 并非对所有设备、所有 kernel 都可用。请用编译器报告、设备属性与 [CUDA occupancy API](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__OCCUPANCY.html) 查实际配置。

<OccupancyLab client:visible />

在实验中输入 256 threads、32 registers、2 KiB shared，得到 8 块和 100%；再输入 1024、32、8，得到 2 块和 100%；最后只把后一配置的 registers 改成 64，得到 1 块和 50%。模型没有寄存器分配粒度、spill 和 GPU 时间，不能替你选 tile。延迟是一次操作完成所需时间，吞吐是单位时间完成的工作量；增加可运行 warp 可能提高吞吐，却不会把一次内存请求本身变快。

## Stream 与 event：先保证比较的是同一个计算

为了把两个输入变成适合 GEMM 的布局，假设在 GEMM 前有两个独立准备 kernel：A 处理左输入，B 处理右输入，C 执行分块 GEMM。C 必须等 A 和 B 的结果；A 与 B 可以尝试并发。这三个名字是**同一次矩阵乘的准备与消费阶段**，不是三个互不相关的任务。

一个 CUDA stream 内的操作按入队顺序执行。放进同一 stream，A、B、C 顺序正确；放进两个 stream，CPU 先提交 A 不等于 B 所在 stream 自动等待 A。若 A 在 stream 0，B 和 C 在 stream 1，须在 A 后记录 event，并在 C 前让 stream 1 等这个 event。B 与 C 本来已有同一 stream 的顺序。跨 stream 的依赖由 event 表达，host 无需为此等待整个 GPU。

<StreamTimelineLab client:visible />

图中的**逻辑时间** A=5、B=3、C=2。单 stream 完成于 10；两个 stream 且有 event 时，C 等到 A、B 都完成，从 5 到 7；删掉 event 时，C 可能从 3 开始读取尚未生成的数据。图上的 5 不是“优化后耗时”，而是错误程序的结束时刻。即使换成 A=3、B=5 后恰好读到正确数据，没有依赖的程序仍会随输入和调度变化而出错。

不同 stream 也不保证物理并发：两个 kernel 可能争用执行单元或带宽。默认 stream 有 legacy 与 per-thread 等语义，实验时显式指定 stream 更容易说清顺序。若在 PyTorch 中让张量跨 stream 使用，还须按其 CUDA allocator 规则维护存储生命周期；event 建立执行顺序，不能独自防止内存过早复用。[CUDA 异步执行文档](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html) 与 [PyTorch CUDA 语义](https://docs.pytorch.org/docs/stable/notes/cuda.html) 给出具体契约。

## 三种时间：CPU 提交、设备区间、端到端

若用 CPU 时钟包住一次异步 kernel 调用，结束时 CPU 可能只完成了提交。开始前同步只能清空旧工作，调用**之后**还要等待完成。对于上面的 A、B、C，有三种正当但不同的问题：

| 要回答的问题 | 计时边界 |
| --- | --- |
| GEMM C 自身在设备上的区间 | 与 C 同一 stream 的 start/stop CUDA event，等待 stop |
| A、B、C 组成的设备工作区间 | 先保证两个 stream 的依赖，正确布置跨 stream 边界并等待最终完成 |
| 用户从输入到可用 C 的等待 | CPU 时钟包含必要的准备、传输、提交和最终同步 |

不能把无顺序关系的两个 event 时间戳相减，称为整条跨 stream 链的耗时。event 是进入设备队列的标记；CPU 调用 `record` 的时刻不是该 event 在 GPU 上生效的时刻。下面的图中 event 仅包围 kernel，CPU 端到端边界更宽。

<Figure src="gpu/measurement-boundaries.svg" alt="CPU 提交与结果等待包住传输和 kernel，设备 event 只包住指定队列中的 kernel">横向长度仅示意边界，不是测得的时间。先决定问题，再放时钟与同步。</Figure>

第一次运行还可能包含上下文初始化、分配、JIT 编译或库算法选择。要报告稳定的重复 GEMM，先完成这些准备，再预热、同步，并在相同矩阵、dtype、布局、输出分配策略下重复测量。记录至少中位数和样本范围，说明是否复用同一输入；复用可能改变缓存命中。小 kernel 的 event 间隙还可能包含 host 尚未提交下一项工作的空档。

本仓库现有的可选 [CUDA event 示例](https://docs.pytorch.org/docs/stable/generated/torch.cuda.Event.html)用**预分配的向量加法**单独演示这些计时边界：它报告 event 中位数、最小/最大值以及整批 CPU 提交加等待时间。向量加法不是本节 GEMM 的 tile 对照，也不能拿它的 GB/s 预测矩阵乘。该脚本需要 CUDA-enabled PyTorch 和 NVIDIA GPU：

```sh
python code/gpu/examples/event_timing.py --elements 1000003 --warmup 10 --repeats 30
```

## 从时间换算速率：先说清分母与分子

若实际测到一次 $1024^3$ GEMM 的设备区间为 $t$ 秒，按每次乘加算 2 FLOP，计算速率是 $2\cdot1024^3/t$ FLOP/s。假设 $t=1$ ms，结果约为 2.15 TFLOP/s；**1 ms 只是单位换算示例，不是本仓库的测量**。如果这次运行涉及 A/B 布局准备，算子速率的分母不能偷偷改用只包住 C 的 event 区间。

有效带宽同样要求明确字节口径。G3 两个版本的“逐 block 输入请求”不同，但它们的数学最少输入/输出数组容量相同：A、B 各 4 MiB，C 4 MiB，合计 12 MiB。该容量既不是实际 HBM 流量，也不是 tile 版本的全部 global load 请求。缓存命中、写分配和读放大会使物理计数不同；要判断瓶颈，结合 profiler 的内存指标与[屋顶线模型](/gpu/kernel-design/#屋顶线强度决定上限贴着哪条线)的相应字节定义。向量加法示例按两个输入读、一个输出写算 12 byte/元素；若一百万元素假设耗时 0.1 ms，逻辑有效带宽是 120 GB/s，依然不是实测 HBM 带宽。

## 从错误检查到 profiler：工具分别回答什么

先用 [G3 的 CUDA 程序](/gpu/kernel-design/#验证与边界把三类结论分开)验证 $5\times7$ 乘 $7\times6$、非整除尺寸和整除尺寸。小矩阵暴露越界、边缘补零与同步问题；性能实验再换到固定的 $1024^3$，并比较相同输出与参考实现。float32 累加顺序可不同，所以按 dtype 与 K 长度选择合理容差；不能只看程序没有报错。

```sh
nvcc -O2 -std=c++17 code/gpu/examples/tiled_gemm.cu -o /tmp/tiled_gemm
/tmp/tiled_gemm
compute-sanitizer --tool memcheck /tmp/tiled_gemm
compute-sanitizer --tool racecheck /tmp/tiled_gemm
compute-sanitizer --tool synccheck /tmp/tiled_gemm
```

[Compute Sanitizer](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html) 的 memcheck 看内存访问，racecheck 主要看 shared memory 的数据竞争危险，synccheck 看同步原语，initcheck 可看未初始化 global memory 的使用。它们只检查实际执行的路径与各自覆盖的错误类型；尤其不能将 racecheck 无报告解释为所有跨 block/global 竞争都不存在。Sanitizer 会改变耗时，不能在其中报告正常性能。

正确性通过后，先用 [Nsight Systems](https://docs.nvidia.com/nsight-systems/UserGuide/) 看 CPU 发射、准备 kernel、GEMM、拷贝及空档：慢的是 C，还是 C 前后的排队与提交？若时间集中在 C，再用 [Nsight Compute](https://docs.nvidia.com/nsight-compute/ProfilingGuide/) 查看该 kernel 的寄存器、shared、occupancy、stall 与内存指标，核对“大 tile 减少请求，却可能降低可运行工作”的假设。看到了相关指标，也还需与实际耗时一起解释；occupancy 变高而时间变长可能是 spill 或复用下降。

Nsight Compute 可能为了收集计数器重放 kernel、序列化执行、清理缓存或控制时钟；因此 profiler 下的耗时不必等于正常运行的 event 时间。保留相同输入和采集设置，先用工具定位原因，再回到无 profiler 的计时复测。若问题在请求调度或 CUDA Graph 发射，下一步读 [S6 执行器](/systems/engine-execution/)；若要把实测与设备峰值相比较，读 [S2 单卡的上限](/systems/accelerator/)。

## 练习与核对

<details>
<summary>假想 SM 的 $t=32$ 版本若每 thread 用 64 个寄存器，能驻留几块？能据此断定它比 $t=16$ 慢吗？</summary>

每块 $1024\times64=65536$ 个寄存器，只容 1 块，即 32 个 warp、50% 理论 occupancy。不能断定耗时：它也可能少读数据、提高局部复用。先核对设备限制和编译报告，再测同一 GEMM。
</details>

<details>
<summary>只把 GEMM 从 $1024^3$ 改成 G3 的 $5\times7$ 乘 $7\times6$，大 tile 仍应减少一半 global 输入请求吗？</summary>

不应。两个尺寸下都只需一个输出 block，输入有效元素只有 $5\cdot7+7\cdot6=77$ 个。更大的 tile 增加无效 thread 和填零位置，无法利用“多个输出 block 重复请求”的那部分收益。算强度时必须重新写明形状与边缘条件。
</details>

<details>
<summary>A=3、B=5、C=2，两个 stream 不设 event 时 C 恰好等到了 A，还需要依赖吗？</summary>

需要。B 的时长可能随输入、设备或争用改变；队列之间没有 A 完成再启动 C 的顺序保证。正确的 event 等待是程序契约，不是根据某组时间补出来的优化。
</details>

<details>
<summary>两版的 event 时间分别是 0.8 ms 与 0.7 ms，但端到端请求都为 4 ms，可以写“大 tile 让请求快 12.5%”吗？</summary>

不能。按这组假设数字，C 的设备区间减少 0.1 ms，即相对 0.8 ms 降 12.5%；端到端请求没有变化。应查传输、准备、发射、排队与同步是否主导，且先确认正确性及测量波动。
</details>
