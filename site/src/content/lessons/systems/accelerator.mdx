[S1](/systems/ledger/) 得到两个强度：单请求线性层约 1 FLOP/byte，长上下文的 decode 注意力约 4 FLOP/byte。它们快还是慢，要看这张卡每秒能搬多少字节、每秒能做多少乘加。[G3](/gpu/kernel-design/#屋顶线强度决定上限贴着哪条线) 已经用一台假想设备定义了屋顶线，[G4](/gpu/measurement/) 定义了测量边界；本章把真实产品规格代进去，看 LLM 的两类负载各站在哪一侧，再把分块、融合与测量落到这两类负载上。

## 存储层级：容量、带宽与延迟是三件事

放得下，不等于搬得及；搬得及，不等于一次随机访问的等待可以忽略。

```mermaid
flowchart LR
  disk[主机存储] --> dram[主机内存]
  dram --> hbm[GPU HBM]
  hbm --> l2[L2]
  l2 --> smem[Shared memory]
  smem --> reg[寄存器]
```

权重和 KV 的大头住在 HBM。一次 kernel 如果反复从 HBM 读同一块数据，带宽就被浪费在重复搬运上。Shared memory 和寄存器小得多，但够一个 block 把正在用的 tile 留住。thread、warp、block、grid 与 SM 的对应见 [G1 执行模型](/gpu/execution-model/)，各层存储的访问与同步条件见 [G2 内存与同步](/gpu/memory-and-sync/)。

## 屋顶线把两个峰值收成一个脊点

G3 的屋顶线把两条上限写成一式：可达 FLOP/s 不超过 $\min(\pi,\beta I)$，脊点 $I_{\mathrm{ridge}}=\pi/\beta$，$\pi$ 是算力峰值，$\beta$ 是带宽，$I$ 是算术强度。强度在脊点左边，上限贴着带宽斜线；在右边，上限贴着算力平台。这里只做一件事：把一张真实加速器的数字代进去。

数字取自 [NVIDIA H100 产品页](https://www.nvidia.com/en-us/data-center/h100/) 上 H100 SXM 一列、2026-09-22 读到的数字：80GB 显存，带宽 3.35 TB/s，FP16 Tensor Core 1979 TFLOPS，脚注写明含稀疏。去掉稀疏后的稠密峰值取一半，即 989.5 TFLOPS。产品页会改版，引用这组数时要连同日期和 SXM 这个形态一起写。NVL 那一列是另一组内存和算力，不能混用。

脊点是 $989.5 / 3.35 \approx 295$ FLOP/byte，带宽按 $10^{12}$ 字节/秒理解产品页上的 TB/s。S1 的两个强度都远在脊点左边：

$$
1 \times 3.35 = 3.35 \text{ TFLOP/s},\qquad
4 \times 3.35 = 13.4 \text{ TFLOP/s}.
$$

相对 989.5 的平台，它们大约是 0.3% 和 1.4%。图的右下角把 0 到 10 FLOP/byte 放大，斜线才看得见；主图里这两个点贴在原点。

<Figure src="infra/04-roofline.svg" alt="屋顶线在约 295 FLOP/byte 处进入算力平台，decode 的强度仍在放大图的斜线上">主图的横轴画到 400 FLOP/byte，脊点大约在 295。放大图的纵轴只到 40 TFLOP/s，用来看清 1 和 4 这两个点。</Figure>

### 下界用来对照实测，本身不是实测

单请求 decode 若每个 token 都把 16.06 GB 权重从 HBM 读一遍，并且带宽打满，需要 $16.06 / 3350 \approx 0.0048$ 秒，大约 4.8 ms，对应每秒约 210 个 token。这是权重搬运的下界。真实一步还要读 KV、启动 kernel、做采样，只会更慢。批大小上来以后，同一份权重被多个 token 分摊，这个下界才按 $B$ 下降，直到强度靠近脊点，或者 KV 变成新的大头。

同一模型、8192 token 的 prefill，仅线性层就有约 $1.32\times10^{14}$ FLOP，按一次 FMA 为 2 FLOP 计。除以 989.5 TFLOP/s，计算下界约 0.13 秒。注意力另有约 $3.5\times10^{13}$ FLOP（按完整方阵估算）。长提示因此更接近平台，短请求的 decode 更接近斜线。优化之前先问这次负载站在哪一侧，否则会把一个带宽问题当成算力问题去调。

编程和占用率的进一步阅读从 [CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/) 进入。[Wafer 的 GPU fundamentals](https://github.com/wafer-ai/gpu-perf-engineering-resources#1-gpu-fundamentals) 把编程模型和编译链的原始文档排在一起。其他厂商的加速器同样要分开写容量、带宽和算力，数字以各自的规格表为准，见这份清单的 [Current hardware](https://github.com/wafer-ai/gpu-perf-engineering-resources#6-current-hardware)。

## Kernel：复用与融合决定离上限多远

屋顶线的下界假设数据按必要的次数流过 HBM。[G3](/gpu/kernel-design/) 已经推导分块怎样让一次装载服务多次乘加、融合怎样少写回一次中间结果，这里只看它们在 H100 SXM 上意味着什么。

<Figure src="infra/05-tiling.svg" alt="朴素实现反复读取一行和一列，分块实现把 tile 留在 shared memory">左边每个输出元素都沿 K 维重新读 A 的一行和 B 的一列。右边一个 block 把两块 tile 放进 shared memory，tile 里的乘加共用这次装载，累加完成后再写回 C。</Figure>

按 G3 的逐 block 局部计数，边长 t、每元素 $b_{\mathrm{elem}}$ 字节的方形 tile 输入强度为 $t/b_{\mathrm{elem}}$。bf16 下要到约 295 FLOP/byte 的脊点，需要边长约 590，两块 tile 就超过一个 SM 的共享内存。高性能 GEMM 仍能贴近平台，是因为 L2 让相邻 block 共用装载、HBM 实际读入的字节少于逐 block 相加；这也是 prefill 的大矩阵乘能站到平台上的前提。decode 的矩阵只有 $B$ 行，再好的分块也无法凭空增加每个权重字节被复用的次数，它的上限仍由 S1 的强度决定。

融合在 LLM 里最重要的例子是注意力：不把 $T\times T$ 分数写回 HBM。[S3 FlashAttention](/systems/flash-attention/) 专门推导这一点。融合的收益取决于中间张量有多大，G3 的融合一节说明了它也可能因寄存器压力而变慢。

### Tensor Core 吃特定的形状和类型

Tensor Core 在一条 warp 指令里完成一块小矩阵乘加，输入类型和碎片形状由架构决定。PTX 里的 warp 级矩阵指令列出了这些形状，见 [PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#warp-level-matrix-instructions)。对不上的尺寸会被补齐，或者退回普通 CUDA core。前面引用的 989.5 TFLOPS 是这类指令的稠密 FP16 峰值，不是任意一个 fp16 kernel 的速度。

从框架或 cuBLAS 基线到 Triton、CUTLASS 与手写 CUDA 的选择标准，见 G3 的入口表；[Wafer 清单](https://github.com/wafer-ai/gpu-perf-engineering-resources#3-programming-models-and-profiling) 也按同一思路把 Triton 放在 CUTLASS 前面：先用能说清问题的那一层。

## 测量：先写下可证伪的假设

屋顶线给出的是上限，分块和融合给出的是一种靠近上限的结构。测量要回答的是：这次运行离那条线有多远，时间到底花在 kernel 里面，还是花在两次 kernel 之间。

```mermaid
flowchart LR
  hyp[写下预期站在斜线还是平台] --> line[用时间线确认空档]
  line --> one[只改一个结构]
  one --> again[再测 TTFT 或 TPOT]
```

<Figure src="infra/06-timeline.svg" alt="时间线上 GPU 在通信和发射间隙出现空档">四行分别是 CPU 发射、GPU kernel、HBM 拷贝和网络。格子是教学用的时间形状。白道是下一步该看的地方：先解释空档，再打开单个 kernel。</Figure>

### 一次可以比较的运行要写下这些

两次耗时能相减，前提是下面几项相同，或者差异被写进记录：

| 记录项 | 原因 |
| --- | --- |
| 模型形状、序列长度、批大小、dtype | 它们就是 S1 的账单 |
| GPU 形态、驱动、CUDA、框架版本 | 峰值和 kernel 选择会随版本变 |
| 预热次数、计时区间、是否同步 | 冷启动和异步返回会把启动算进 kernel |
| 正确性对照 | 更快但结果变了，比较的是另一个计算 |

正确性先于速度。越界和竞争可以用 [Compute Sanitizer](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html) 看。数值对照可以是一小段 CPU 结果，或同一个算子的另一个实现，容差要和 dtype 一起写下来。

### 工具与二进制

Sanitizer、Nsight Systems 与 Nsight Compute 各自回答什么问题，以及观测怎样改变运行，[G4](/gpu/measurement/#从错误检查到-profiler工具分别回答什么) 已经分开讲过。这里只补一项：CUDA C++ 先变成 PTX，再变成目标 GPU 的机器码。PTX 的语义在 [PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)，`cuobjdump` 和 `nvdisasm` 用来查看二进制里实际生成了什么，说明见 [CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)。它用来核对“我以为会发出 Tensor Core 指令”这件事，不代替时间线。编译选项、架构代号和输入形状都会改变产物，所以它们属于上面的记录项。

### 一次只改一个量

一次实验里同时改 tile、dtype 和启动方式，快了也无法知道是哪一项生效。可执行的循环是：用屋顶线的下界写下预期站在斜线还是平台，用时间线确认时间是否真在那个 kernel 里，只改一个结构，再测端到端的 TTFT 或 TPOT。Kernel 内部变快，而端到端不变，通常说明空档在别处。

## 练习与核对

<details>
<summary>1. 只看线性层、忽略 KV，8B 模型的 decode 批大小要到多少，才碰到 H100 SXM 的脊点？</summary>

线性层理想强度等于批大小 $B$，脊点约 295 FLOP/byte，所以 $B\approx295$。实际上远在这之前 KV 就会进入分母：[S1](/systems/ledger/) 的练习按实际线性矩阵计费后，16 条 8192 token 请求时强度只剩约 7.46，长上下文的 decode 很难靠增大批大小走到平台上。

</details>

<details>
<summary>2. 一个 kernel 的强度是 8 FLOP/byte，在 H100 SXM 上它的上限是多少？该先优化什么？</summary>

$8\times3.35=26.8$ TFLOP/s，约为平台的 2.7%，仍在带宽斜线上。先减少 HBM 字节——复用 tile、融合掉中间张量、降低数据位宽——而不是调算力相关的参数。

</details>

<details>
<summary>3. 把 tile 大小和 dtype 同时改掉，端到端快了 20%。这个结论能写进报告吗？</summary>

只能写“两处改动合起来快了 20%”，不能归因给其中任何一项：dtype 改变了字节数和可用的 Tensor Core 指令，tile 改变了复用和占用率，二者的效果可能互相抵消或叠加。还要确认正确性对照在新 dtype 下仍在容差内，否则比较的是另一个计算。

</details>
