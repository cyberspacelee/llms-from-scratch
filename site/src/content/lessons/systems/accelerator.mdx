[S1](/systems/ledger/) 为同一个 8B 形状算出两种负载：8192 token 的提示一次进入 prefill；随后一次 decode 只生成一个新 token，却读回已有 KV。两者都运行在 GPU 上，为什么优化方向会不同？本章把 S1 的运算量和字节数放进 [G3 屋顶线](/gpu/kernel-design/)；[G4 测量](/gpu/measurement/) 已介绍计时边界，这里把它用于推理实验。

## GPU 提供两种速率，数据经过多个存储层级

权重和 KV cache 的大部分常驻 HBM（GPU 显存）。一个 kernel 把当前要用的片段搬到 L2、shared memory 或寄存器后，可能在片上多次使用。容量回答“能否放下”，HBM 带宽回答“每秒能搬多少字节”，计算吞吐回答“每秒能做多少浮点运算”；三个数字不能互相替代。[G1](/gpu/execution-model/) 和 [G2](/gpu/memory-and-sync/) 已解释线程、SM 与这些存储位置的关系。

```mermaid
flowchart LR
  HBM[HBM：权重与 KV] --> L2[L2 cache]
  L2 --> SM[SM：shared memory 与寄存器]
  SM --> TC[计算单元：乘加]
```

读图时关注往返次数：若一块权重从 HBM 进来后服务 8192 个输入位置，计算量相对搬运量很大；若它只服务一个位置，搬运量可能先成为限制。图只表示数据路径，不表示各级存储的真实延迟或容量比例。

本章用 [NVIDIA H100 官方规格表](https://www.nvidia.com/en-us/data-center/h100/) 的 **H100 SXM** 一列（2026-09-28 核对）：80 GB HBM、3.35 TB/s 带宽、FP16 Tensor Core 1979 TFLOP/s。该算力数字的脚注是 *with sparsity*；下面假设稠密计算，取其一半约 **989.5 TFLOP/s**。这里的 TB 和 TF 都按 $10^{12}$ 计。80 GB 是容量，不参与速率除法；H100 NVL 是另一种形态，不能把两列规格拼在一起。

## 屋顶线：先判断哪种峰值更紧

令 $F$ 是 FLOP 数（一次融合乘加计 2 FLOP），$D$ 是**从 HBM 搬运**的字节，算术强度 $I=F/D$，单位 FLOP/byte。若计算峰值为 $\pi$、HBM 带宽峰值为 $\beta$，完成时间 $t$ 同时满足 $t\ge F/\pi$ 和 $t\ge D/\beta$。因此

<KeyEq label="单卡的理想时间下界">

$$
t\ge\max\left(\frac{F}{\pi},\frac{D}{\beta}\right),\qquad
P=\frac Ft\le\min(\pi,\beta I).
$$

</KeyEq>

两个时间取**较大值**，因为理想设备可以重叠计算与搬运；将二者相加不是通用下界。两项相等时的强度叫脊点：$I_{\mathrm{ridge}}=\pi/\beta=989.5/3.35\approx295.37$ FLOP/byte。低于脊点，带宽给出的吞吐上限更紧；高于脊点，计算峰值更紧。它是上限的分类，不是对实测瓶颈的诊断。

<Figure src="infra/04-roofline.svg" alt="H100 SXM 的理论屋顶线在约 295 FLOP/byte 转平，1 与 4 FLOP/byte 两点位于放大的带宽斜线上">主图的脊点约为 295；右侧放大 0–10 FLOP/byte，才能看清 S1 中单请求线性层的 1 与 decode 注意力的 4。这两个点是分别计费的子计算，不代表整步 decode 的强度。</Figure>

## 一次 decode：合并线性层与 KV 的运算和搬移量

沿用 S1 的 Llama 3 8B 公开形状、bf16 权重、batch size $B=1$、KV 长度 $T=8192$。S1 算出本步实际执行的稠密矩阵权重数 $N_{\mathrm{linear}}=7504658432$，其中包含输出头；词 embedding 只查一行。总参数 $8030261248$ 用于常驻容量，不能全按矩阵乘读一次。假设线性权重从 HBM 各读一次，而本步注意力读完已有 KV，得到：

| 账目 | 运算量 $F$ | HBM 字节 $D$ | 强度 $F/D$ |
| --- | ---: | ---: | ---: |
| 稠密线性层 | $2N_{\mathrm{linear}}=15.009$ GFLOP | $2N_{\mathrm{linear}}=15.009$ GB | 1 FLOP/byte |
| 32 层 decode 注意力的 $QK^\top$ 与 $AV$ | $2^{32}=4.295$ GFLOP | KV 为 $2^{30}=1.074$ GB | 4 FLOP/byte |
| 两项合计 | 19.304 GFLOP | 16.083 GB | 约 1.20 FLOP/byte |

第三行才是这一组**简化估算**的合计强度。它仍远低于 295.37，所以按规格计算的带宽上限为 $3.35\times1.20\approx4.02$ TFLOP/s，时间下界是

$$
t_{\mathrm{decode}}\ge
\max\left(\frac{19.304\times10^9}{989.5\times10^{12}},
\frac{16.083\times10^9}{3.35\times10^{12}}\right)
\approx4.80\ \mathrm{ms}.
$$

第一项只有约 $0.020$ ms。这个 4.80 ms 是本模型、单请求、假定数据都从 HBM 读且达到标称带宽时的**必要数据搬运时间**；不能写成“这张卡每 token 实测 4.80 ms”。实际还要执行 norm、RoPE、softmax、采样、kernel 发射和缓存写入。若数据命中 L2，实际 HBM 字节会改变；若批中多条请求共用一次权重读取，权重项也会被摊薄。应重新计数后再应用公式。

## 同一模型的 prefill：权重复用改写强度

先用下面的实验检查上一节的 decode 估算，再计算 prefill。实验只计算 decode 的线性层与 KV 主项。

<RooflineLab client:visible />

保持 T=8192，把 B 从 1 改为 8，观察算术强度与点的位置。权重读取由多条请求共用，但 KV 仍逐请求读取。再固定 B=8，把 T 增至 16384，检查更多 KV 读取怎样改变强度。

横轴是对数刻度，屋顶线采用前述 H100 SXM 的稠密假设。图下两个时间下界取较大值。实验没有计算 prefill 的全部 HBM 流量，也没有设备测量数据。

仍用这条 8192 token 提示，但假设推理执行器**只对最后一个位置计算输出头**。S1 的层内权重为 $N_{\mathrm{blocks}}=6979321856$，输出头为 $N_{\mathrm{head}}=525336576$，所以线性层运算量是

$$
F_{\mathrm{linear,prefill}}=2T N_{\mathrm{blocks}}+2N_{\mathrm{head}}
\approx114.35\ \mathrm{TFLOP}.
$$

这里不能用 $2T N_{\mathrm{linear}}$：那会把只在末位置执行的输出头乘上 8192。若 causal attention 的实现跳过未来位置，其 $QK^\top$ 与 $AV$ 主项约为 $2n_{\mathrm{layers}}dT(T+1)=17.59$ TFLOP；若按完整方阵执行，则约 35.18 TFLOP。前一种理想计算时间下界为 $(114.35+17.59)/989.5\approx0.133$ s。

Prefill 把许多位置一起交给大矩阵乘，让同一块层权重服务更多输入，因而**有机会**比 decode 更接近计算平台。但 $0.133$ s 只是用全部 FLOP 和 FP16 Tensor Core 峰值相除；它并未计算 prefill 的全部 HBM 流量，不能单凭这一个数断言整段 prefill 已经计算受限，更不能当作 TTFT。是否真正使用 Tensor Core、因果 tile 是否跳过、激活的读写和实际执行时间都需测量。

## 优化应改变哪一项账目

[G3](/gpu/kernel-design/) 已推导分块与融合。放在本章的负载里，它们分别改变以下条件：

| 做法 | 期望改变 | 需要检查的代价 |
| --- | --- | --- |
矩阵乘分块 | 一块权重或激活进片上后服务更多乘加，减少 HBM 重读 | tile 太大可能占满寄存器/shared memory，使可同时运行的 block 变少 |
融合中间步骤 | 少写回、少读回临时张量，并可能少一次 kernel 发射 | 寄存器压力、计算顺序与数值误差可能变化 |
批量 decode | 多个新 token 共用一次权重读取 | 每条请求的 KV 仍要分别读取，容量与延迟也随并发变化 |
Tensor Core 路径 | 提高适配矩阵乘的实际计算吞吐 | 规格峰值不适用于任意元素级 kernel；dtype、形状与指令路径要核对 |

例如，单请求 decode 的线性层即使把内部 tile 做得更好，也无法让一份权重凭空服务更多请求。反过来，长提示 prefill 的矩阵乘已经有跨位置复用，只盯着降低权重字节可能错过计算效率。下一章 [S3 FlashAttention](/systems/flash-attention/) 将以注意力为例：不物化完整的 $T\times T$ 分数，减少中间数据的显存往返。省了逻辑字节并不保证端到端速度按同一比例上升。

## 从理论下界到可比较的测量

先固定同一 checkpoint、GPU 形态、dtype、提示和输出长度、batch、框架与 kernel 版本。预热后分开记录 prefill、稳态 decode、端到端 TTFT 与输出间隔；GPU 异步运行，计时区间必须同步或用设备事件。对照输出要在约定的 dtype 容差内一致。[G4](/gpu/measurement/) 给出具体计时和 profiler 用法。

想检验“单请求 decode 主要受 HBM 搬运限制”，先记录实际 HBM 读写字节与 kernel 时间，再计算 $F/t$ 和 $D/t$。若时间主要落在 kernel 之间的发射空档，改内核带宽不会等比例改善用户延迟。若同一个 kernel 的实际 HBM 字节明显高于估算值，应查重复读取、临时张量或内存访问；明显低于估算值，应查缓存命中和测量范围。然后只改一个结构，重新测相同请求分布。

三个指标的测量对象不同：

| 指标 | 回答的问题 |
| --- | --- |
| occupancy | SM 上已驻留 warp 数占可驻留上限的多少？ |
| GPU utilization | 采样区间内 GPU 是否有任务活动？ |
| 屋顶线达成率 | 同一边界的实测速率 $F/t$ 达到 $\min(\pi,\beta I)$ 的多少？ |

occupancy 和 GPU utilization 高，不代表接近 Tensor Core 或 HBM 峰值。计算达成率时，要使用实际 HBM 字节与对应的 FLOP 计数。上表的简化逻辑字节不能当作 profiler 读数。[NVIDIA CUDA 最佳实践](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#bandwidth) 也区分理论带宽、有效带宽和实际搬运。

## 练习与核对

<details>
<summary>只看同一模型的线性层，把 decode 的 batch size 改为 8，且一份权重仍只从 HBM 读一次。强度和带宽上限是多少？</summary>

运算量变为 $2N_{\mathrm{linear}}\times8$，权重字节仍为 $2N_{\mathrm{linear}}$，所以强度为 8 FLOP/byte，带宽上限 $8\times3.35=26.8$ TFLOP/s。这个计算故意只看线性层；若加上 8 条请求各自的 KV，强度会下降，不能把 26.8 当作整步 decode 的上限。

</details>

<details>
<summary>如果一个算子的实测执行时间为 6 ms，而规格给出的计算下界为 1 ms、搬运下界为 4 ms，能断言它已打满 HBM 带宽吗？</summary>

不能。理论下界是 $\max(1,4)=4$ ms，6 ms 只说明还有至少 2 ms 没被这个理想模型解释。实际 HBM 字节、带宽利用、发射空档、同步和形状效率都可能改变判断；必须在相同计时边界下测字节与时间。

</details>

<details>
<summary>Prefill 的输出头若改为每个位置都计算 logits，哪项公式变了？</summary>

线性主项从 $2TN_{\mathrm{blocks}}+2N_{\mathrm{head}}$ 变成 $2T(N_{\mathrm{blocks}}+N_{\mathrm{head}})$；注意力的 $T(T+1)$ 项不因这个选择改变。训练或逐位置评估可能需要全部 logits，生成首 token 的执行器则可以只投影最后位置。两种策略的 FLOP 估算不同。

</details>
