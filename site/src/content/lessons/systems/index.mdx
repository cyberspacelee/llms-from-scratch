用户发来一段 prompt，模型开始生成后续 token。单次前向的结果可以正确，但服务仍可能因显存不足、请求排队或数据搬移而变慢。本路线沿这条请求追问三件事：它占用多少资源，系统怎样同时执行多条请求，改动后用户实际得到了什么。开始前先读 [P11 生成](/principles/generation/) 和 [P12 KV cache](/principles/kv-cache/)；后者证明了只计算新增 token 仍能保持整段计算的结果。

## 先算清一次前向

| 问题 | 章节 | 核对结果 |
| --- | --- | --- |
| 权重、KV 和一次前向各需要多少资源？ | [S1 资源估算](/systems/ledger/) | 分开计算容量、FLOP 和搬移字节 |
| 设备带宽与算力给出什么限制？ | [S2 单卡上限](/systems/accelerator/) | 在明确假设下求理想时间下界 |
| 怎样减少注意力中间张量的读写？ | [S3 FlashAttention](/systems/flash-attention/) | 分块更新 softmax，核对输出不变 |

这里需要知道 GPU 的 thread 怎样负责输出、分块为何能复用数据，以及怎样测量异步执行；这些先修在 [G1–G4 GPU 路线](/gpu/) 中逐步建立。读过 S2 后再看 S3，就能把“算得一样”和“可能搬得更少”分开判断。

## 再让多条请求共用设备

| 问题 | 章节 | 核对结果 |
| --- | --- | --- |
| 本轮处理哪些输入位置？ | [S4 连续批处理](/systems/engine-runtime/) | 区分已采样 ID 与已写入 KV |
| 逻辑位置放在哪个物理块？ | [S5 分页 KV cache](/systems/paged-cache/) | 核对共享、复制与释放的条件 |
| 请求清单怎样变成 GPU 输入？ | [S6 引擎执行器](/systems/engine-execution/) | 对齐位置、槽位、有效长度与 Graph 地址 |

两条请求可以共用一次前向，但各自只能读取自己的有效历史。这三章分别建立调度、地址与执行上的保证。

## 最后比较改动的代价与收益

| 改动 | 章节 | 必须一起比较的量 |
| --- | --- | --- |
| 改变权重或 KV 的表示 | [S7 量化](/systems/quantization/) | 存储字节、数值误差、实际执行 |
| 先提出多个草稿 token，再由目标验证 | [S8 推测解码](/systems/speculative-decoding/) | 目标采样分布、节省的调用、新增工作 |
| 切分权重与请求状态 | [S9 多卡推理](/systems/cluster/) | 通信、等待、容量与吞吐 |

质量比较可回读 [T4 模型评估](/training/evaluation/)。读 S9 时，再回看 S6 的多卡执行细节。

这些改变最终都要回到 [S10 服务评估](/systems/serving-evaluation/)：从客户端事件计算首 token 延迟、后续输出间隔和满足服务目标的吞吐，并记录负载与失败请求。一个 kernel 更快、模型更小或 GPU 更多，都只是中间证据；只有固定模型质量与请求分布、明确计时边界，才能判断这条请求是否真的得到改善。


## 按缓存语义选择分支

[混合缓存边界](/systems/hybrid-cache/) 在全局 KV、滑窗 KV 与递推状态之间寻找可以共同恢复的边界；[滑窗缓存实现](/systems/window-cache/) 用环形地址保存限定历史。它们以主路线的地址与提交规则为先修，按架构需要阅读，不夹在所有服务请求的必读链中。
