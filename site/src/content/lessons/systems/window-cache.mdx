## Ring cache：同一窗口算子的两种执行方式

只保留最近三个位置的键和值时，物理存储可用三个 slot。逻辑位置 $p$ 写到 $p\bmod3$，每个 slot 记绝对位置 tag。位置 5 已写入时：

| 逻辑位置 | 3 | 4 | 5 |
| --- | ---: | ---: | ---: |
| 物理 slot $p\bmod3$ | 0 | 1 | 2 |
| slot 的绝对 tag | 3 | 4 | 5 |

写位置 6 会覆盖 slot 0 中的位置 3；查询 6 所需的恰好是 $4,5,6$。查询先计算逻辑可见集合，再找 slot 并核对 tag。RoPE 继续用绝对位置 6，不能用 slot 0 作为旋转位置，否则相位每三步重复。

<WindowCacheLab client:visible />

实验上排是可见的逻辑位置，下排是循环复用的物理 slot。保持窗口 3，先核对位置 5 的可见集合 `{3,4,5}`。再把查询位置改为 6：集合变成 `{4,5,6}`，slot 0 的 tag 从 3 变成 6。RoPE 的逻辑位置仍为 6，不能随 slot 变成 0。

这个交互只计算可见集合和地址。前向等价由配套脚本核对：固定参数和位置规则，逐 token 写缓存的结果应与**从完整前缀按同一窗口 mask 重算的前向**一致。多层时，只拿剩余的原始 token 从头计算会丢失早期信息。完整注意力使用另一组候选，其输出 2.5 不属于这里的等价参照。

等价还有执行前提。单 token 追加时，先写当前位置再读窗口，过期位置恰可覆盖。若把超过窗口的整块新键先写进三格 ring，较早新查询需读的历史可能已被较晚 token 覆盖。应逐步执行或暂存还会被读的状态；tag 可发现错读，但不会自动修复顺序。

<details>
<summary>窗口3，逻辑位置5写哪个ring槽？注意力位置编码是否也用这个槽号？</summary>

写槽 $5\bmod3=2$；位置编码仍用5。槽2以前的旧数值已经失效，读取时需按有效逻辑位置检查，不能把同槽看成同一token身份。

</details>

<details>
<summary>把输入截为最后3个token再从第一层完整重算，为什么可能不同于多层滑动窗口缓存？</summary>

旧token在更低层形成隐藏状态时曾看过其当时窗口。缓存保留了这些已经形成的K/V；截短重算改变了旧token的前缀条件。正确参照应是同一个窗口模型从序列开始执行。

</details>
