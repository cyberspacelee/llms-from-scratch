[P8 Decoder](/principles/modern-decoder/) 给出了每层的矩阵，[P10 KV cache](/principles/kv-cache/) 说明了生成时保存什么。现在要回答一个系统问题：**一条提示到达后，模型占多少空间，处理提示做多少运算，下一步生成又要读写多少数据？** 本章只研究稠密、无偏置、使用 GQA 和 SwiGLU 的 Decoder；权重与 KV 都按每元素 2 字节计算。先用可手算的模型完成整张账，再代入公开模型。FLOP 是运算量，FLOP/s 才是速率；一次乘加计 2 FLOP。

## 固定模型和请求：每个数字属于哪里？

令教学模型 S 有两层，隐藏维度 $d=4$，查询头数 $n_q=2$，KV 头数 $n_{\mathrm{kv}}=1$，每头维度 $d_h=2$，前馈维度 $d_{\mathrm{ff}}=8$，词表大小 $n_{\mathrm{vocab}}=16$。每层有两个 RMSNorm，末尾再有一个；embedding 与输出头**绑定为同一块参数**。两个查询头共用一组 K/V，这是 GQA 共享机制的 MQA 极端情形。

固定一条请求：先对 4 个提示 token 做 **prefill**（一次处理提示并建立 KV cache），由末位置的 logits 选出下一个 token；下一次将这个新 token 输入模型，做一步 **decode**（只处理新增位置），此时可见长度是 5。这里数的是这一轮前向，不把采样操作和后续生成步骤暗中加进去。

| 时刻 | 输入模型的位置数 | 本步查询数 | 计算后缓存长度 | 输出头调用 |
| --- | ---: | ---: | ---: | --- |
| prefill | 4 | 每层 4 个 | 4 | 只投影最后位置 |
| decode 一步 | 1 | 每层 1 个 | 5 | 投影新增位置 |

读到第五个 token 之前，虽然它已被采样出来，缓存仍只有前四个位置；这个时序在 [P10](/principles/kv-cache/#prefill-后为什么只保存-kv) 中有逐位置核对。

## 参数数量：先列矩阵，再去重

按行输入的 $XW$ 记法，一层中 Q、K、V、O 四个投影与 SwiGLU 的三块矩阵分别是：

| 矩阵 | 形状 | 参数个数 |
| --- | --- | ---: |
| $W_Q,W_O$ | $4\times4$，各一块 | $16+16=32$ |
| $W_K,W_V$ | $4\times2$，各一块 | $8+8=16$ |
| $W_{\mathrm{gate}},W_{\mathrm{up}},W_{\mathrm{down}}$ | 前两块 $4\times8$，后一块 $8\times4$ | $32+32+32=96$ |

所以每层线性权重有 $144$ 个，两层是 $N_{\mathrm{blocks}}=288$。一般形状下，只要 $n_qd_h=d$，相同的式子是

$$
N_{\mathrm{blocks}}=n_{\mathrm{layers}}\left[2d(n_qd_h)+2d(n_{\mathrm{kv}}d_h)+3dd_{\mathrm{ff}}\right].
$$

RMSNorm 每次只训练一个长度为 $d$ 的缩放向量；两层各两次、末尾一次，共 $N_{\mathrm{norm}}=(2n_{\mathrm{layers}}+1)d=20$。词表表有 $N_{\mathrm{embed}}=n_{\mathrm{vocab}}d=64$ 个参数。模型 S 绑定输出头与 embedding，所以**存储时只收一次**：

<KeyEq label="模型 S 的唯一参数与权重字节">

$$
N_{\mathrm{total}}=288+20+64=372,\qquad
M_{\mathrm{weight}}=372\times2=744\text{ 字节}.
$$

</KeyEq>

绑定不代表输出投影免费。输入时只按 ID 读取 embedding 的一行（$4\times2=8$ 字节）；生成 logits 时仍要把隐藏状态与整个 $16\times4$ 词表表相乘。因而参与本步**稠密矩阵乘**的参数个数是 $N_{\mathrm{linear}}=N_{\mathrm{blocks}}+N_{\mathrm{head}}=288+64=352$，既不等于唯一参数的 372，也不含 RMSNorm 的元素级运算。若不绑定，唯一参数会增为 $436$，但 $N_{\mathrm{linear}}$ 仍是 352。

## KV 容量账：存了多少，与这一步读了多少不同

每层每个位置保存一份 K、一份 V，各有 $n_{\mathrm{kv}}d_h$ 个数；不保存历史 Q。$b_{\mathrm{elem}}$ 表示一个缓存元素的字节数，于是

<KeyEq label="每个已处理 token 的 KV 容量">

$$
m_{\mathrm{KV/token}}=2n_{\mathrm{layers}}n_{\mathrm{kv}}d_hb_{\mathrm{elem}}
=2\times2\times1\times2\times2=16\text{ 字节}.
$$

</KeyEq>

prefill 后缓存占 $4\times16=64$ 字节。decode 输入第五个 token 后占 $5\times16=80$ 字节，新增写入 16 字节。为了给第五个位置算注意力，它需要读取包括当前位置在内的五组 K/V，**逻辑上**共 80 字节。这不是额外再分配 80 字节；它是对已存数据的一次读取估计。实际 HBM 流量还受 cache 命中、GQA 头间复用、内存布局、融合和 kernel 实现影响，不能由容量直接断定。

## 运算账：prefill 与 decode 走同一组权重

先数线性层。一个输入位置经过一个权重就做一次乘加，按 2 FLOP 计。prefill 的四个位置都穿过两层矩阵，但只需最后位置的输出 logits；decode 只有一个新增位置：

$$
\begin{aligned}
F_{\mathrm{linear,prefill}}&=2(4N_{\mathrm{blocks}}+N_{\mathrm{head}})
=2(4\times288+64)=2432,\\
F_{\mathrm{linear,decode}}&=2(N_{\mathrm{blocks}}+N_{\mathrm{head}})=704.
\end{aligned}
$$

若训练要对四个位置全部算 logits，前一式会变为 $2\times4(N_{\mathrm{blocks}}+N_{\mathrm{head}})=2816$；不要把输入 embedding 按整张词表矩阵乘重复收费。计数省略了 RMSNorm、SiLU、RoPE、softmax、残差和采样的元素级运算。

注意力另算。一个查询与一个键求点积约需 $2d_h$ FLOP，再用注意力权重加权一个值约需 $2d_h$ FLOP，合计每个**可见的查询-键对**约 $4d_h$ FLOP。prefill 的 4 个因果查询分别看见 1、2、3、4 个键，合计 $4(4+1)/2=10$ 对；decode 的新查询看见 5 个键。两层、每层两个查询头，因此

$$
F_{\mathrm{attn,prefill}}=4d_hn_qn_{\mathrm{layers}}\frac{4(4+1)}2=320,\qquad
F_{\mathrm{attn,decode}}=4d_hn_qn_{\mathrm{layers}}\times5=160.
$$

GQA 让两个查询头共享缓存，却没有减少这两个头各自的点积与加权运算。上式按因果可见对计理论乘加；若实现仍计算整块 $4\times4$ 分数再 mask，实际执行的 FLOP 会更多。若 softmax 与中间分数写回 HBM，流量也更多。[S3](/systems/flash-attention/) 再看如何减少这种中间搬移。

把三笔主项排在一起，可以在不换模型的前提下看到阶段差异：

| 资源 | prefill，4 个位置 | decode，输入第 5 个位置 |
| --- | ---: | ---: |
| 已存 KV | 64 字节 | 80 字节 |
| 本步 KV 逻辑读取 | 算法相关，不能把容量当流量 | 80 字节 |
| 本步新增 KV 写入 | 64 字节 | 16 字节 |
| 线性层乘加 | 2432 FLOP | 704 FLOP |
| 注意力可见对乘加 | 320 FLOP | 160 FLOP |

## 数据搬移账：强度何时能用来判断瓶颈？

**算术强度** $I$ 是 FLOP 除以所讨论存储层级实际搬运的字节，单位 FLOP/byte。先做一个明确的理想化：decode 批中有 $B$ 条请求，同一份稠密权重从 HBM 读一次并供 $B$ 个新 token 使用；权重每元素 2 字节，暂不收 KV、embedding 行、输出、norm 和其它流量。于是

<KeyEq label="仅线性层、仅权重流量的强度">

$$
I_{\mathrm{linear/weight}}
=\frac{2BN_{\mathrm{linear}}}{2N_{\mathrm{linear}}}
=B\text{ FLOP/byte}.
$$

</KeyEq>

模型 S 单请求时，704 FLOP 对应理想化的 704 字节权重读取，强度为 1。若把本步五个位置的 KV 读取 80 字节与新增写入 16 字节也计入，且分子加入注意力的 160 FLOP，则这个**部分账**为 $(704+160)/(704+80+16)=1.08$ FLOP/byte。实际强度必须用实际搬移字节和实际执行 FLOP 计算；这还漏了输入行、norm 和输出等流量。

当 $B$ 增大，权重可以摊到更多请求，但每条请求有自己的 KV。长上下文时缓存读取会抬高分母；能否复用、是否放得下、能跑多快是三个问题。容量由参数与缓存长度决定，理论 FLOP 由算子与可见位置决定，时间则需要设备带宽、算力与实测。[S2](/systems/accelerator/) 将把强度放到 GPU 屋顶线上。

## 代入公开形状：Llama 3 8B 的量级

这一步**换模型而不换公式**。Meta 的 [Llama 3 模型配置](https://github.com/meta-llama/llama-models/blob/main/models/sku_list.py) 列出 8B 的 $d=4096$、$n_{\mathrm{layers}}=32$、$n_q=32$、$n_{\mathrm{kv}}=8$、词表大小 128256、前馈系数 1.3 与 1024 对齐。[官方实现](https://github.com/meta-llama/llama3/blob/main/llama/model.py) 以 $d_h=d/n_q=128$ 计算头维度，按 $\lceil\lfloor1.3\lfloor(2/3)(4d)\rfloor\rfloor/1024\rceil\times1024$ 得到 $d_{\mathrm{ff}}=14336$，并分别创建 embedding 与输出头。本段来源于 2026-09-28 核对；以下是结构估算，不是读取 checkpoint 或测 GPU 峰值。

| 项目 | 按上面公式得到 |
| --- | ---: |
| 32 层线性矩阵 $N_{\mathrm{blocks}}$ | 6,979,321,856 个参数 |
| embedding 与输出头 | 各 525,336,576 个参数，不绑定 |
| 65 个 RMSNorm 向量 | 266,240 个参数 |
| 唯一参数 $N_{\mathrm{total}}$ | 8,030,261,248 个 |
| bf16 权重存储 | 16,060,522,496 字节，约 14.96 GiB |
| 每 token 的 bf16 KV | 131,072 字节，即 128 KiB |

因此一条已经处理 8192 个 token 的请求，其 KV 容量是 $8192\times128\text{ KiB}=1\text{ GiB}$；16 条同长度请求是 16 GiB。下图只画静态容量，未包括临时激活、分配器碎片或权重之外的运行时对象。

<Figure src="infra/01-ledgers.svg" alt="Llama 3 8B 的 bf16 权重约 14.96 GiB，十六条 8192 token 请求的 KV 为 16 GiB">纵轴按 GiB 比较唯一权重与 KV 容量；请求数增长时，后者线性增加。图中的权重数已包含小量 RMSNorm，四舍五入后刻度不变。</Figure>

8B 的本步稠密权重数是 $N_{\mathrm{linear}}=6,979,321,856+525,336,576=7,504,658,432$；单请求 decode 的线性主项约 $1.501\times10^{10}$ FLOP，理想化权重读取约 15.01 GB。8192 长度的注意力主项是 $4\times32\times4096\times8192=2^{32}$ FLOP；对应的 KV 容量为 $2^{30}$ 字节。若每份 KV 从 HBM 恰读一次，仅这两项之比是 4 FLOP/byte。它是给 [S2](/systems/accelerator/) 用的理想化输入，不是观测到的 kernel 强度。

## 边界：估算何时失效？

- $2N$ 只适用于确实执行的稠密矩阵乘；embedding 查表、RMSNorm 和绑定头的去重各有自己的计数。训练的反向与优化器状态需要另一张账，见 [T2](/training/optimization/)；常见混合精度 Adam 布局还会有主权重、梯度与两个矩状态，不能把推理的 2 字节/参数直接当训练显存。
- KV 的**容量**按已缓存位置算，**流量**按本步访问算。GQA 改变 KV 宽度，不等于改变查询头数；滑动窗口、量化 KV、分页管理或缓存命中会改写某些项，见 [S5](/systems/paged-cache/) 与 [S7](/systems/quantization/)。
- 只统计可见对的注意力 FLOP 是算法下界形状。完整分数矩阵的计算、softmax、分数写回、融合、padding 和 kernel 调度都会让执行账不同。MoE/MLA 不满足这里的稠密 GQA 前提，见 [A1](/advanced/moe/) 与 [A2](/advanced/mla/)。

## 练习与核对

<details>
<summary>模型 S 不绑定输出头，其他不变。唯一参数、权重字节、本步线性 FLOP 各是多少？</summary>

输出头新增一块 $16\times4=64$ 个参数，唯一参数从 372 变为 436，按每元素 2 字节是 872 字节。执行时本来就需要投影到全部词表，$N_{\mathrm{linear}}=352$ 不变，所以 decode 线性主项仍为 704 FLOP。存储去重与执行次数是两回事。

</details>

<details>
<summary>模型 S 的提示从 4 个 token 变成 8 个，接着输入第 9 个。KV 容量、这一步的注意力主项和线性主项各是多少？</summary>

每位置 KV 仍为 16 字节；prefill 后 128 字节，输入第 9 个后 144 字节。新查询每层每头看见 9 个键，所以注意力是 $4\times2\times2\times2\times9=288$ FLOP。层内矩阵和输出头形状没有变化，decode 线性主项仍为 704 FLOP。长度改变的是缓存和注意力配对，不是这一步执行的线性权重个数。

</details>
