# 课程章节重写规范

目标读者具备 Python 基础，正在建立深度学习和 LLM 的完整概念链。章节的任务是让读者独立解释、计算并检验一个问题，而不是收集相关术语。逐页重写时同时阅读本页、前一章结尾、下一章开头和 `CHAPTER_BLUEPRINTS.md`；设计卡是线索，若与实际教学顺序冲突，以可验证的读者路径为准。

## 先设计学习路径

1. 写出本章结束后读者能独立完成的一件事，并列出必要先修。不要把上一章全部内容默认视为先修。
2. 画出核心概念的依赖顺序。每节应回答开篇问题的一个具体子问题；无法说明作用的内容移到主线完成后的延伸阅读，或另开章节。
3. 选一个贯穿的、足够小而不失真的案例。定义、公式、手算、图、代码尽量使用同一组对象和记号；更换数据、模型或假设时，明确说明为何更换、哪些条件保留。
4. 从案例遇到的障碍引入新概念，解释定义、成立条件和直观含义，再逐步推导并回到案例。公式前说明目标，公式后解释每一步与结果的用途。
5. 先完成主问题，再讨论反例、边界、实现变体和进阶证明。先修尚未出现的推导不可穿插在必读路径中；需要时给出可直接理解的数值直观，并把证明放在后续章节或章末选读。
6. 在关键推导后安排一个完整例题、一个只改变少量条件的练习，以及能暴露误解的反例或边界案例。答案须解释理由。图必须承载文字难以清晰表达的关系，并在正文中被解读。

“深入”不按字数、公式数或组件数判断。至少说明为什么需要、推导依据、适用条件、会错在哪里、如何用独立例子验证。确实需要两个独立先修链或两个不同验收目标时，拆章；不要为了固定篇幅把它们挤在一起。

## 连贯性与深度验收

重写前先列一张简短的概念依赖表：本章从上一章实际学会的哪项能力出发，新增哪项能力，下一章具体使用哪项结果。标题、例题、图、代码和练习都应推进这条链。若删去某节不影响回答本章问题，就将它移到主线之后的选读、相邻章节或独立章节；不要用更多过渡句掩盖章节边界错误。

主线只保留一个可复算的案例。第一次引入新符号时指出它在案例中的对象；每次推导后先把结果代回案例，再切换到一般式。复杂表格只能汇总已经解释的概念，不能首次介绍多个术语。代码和图应回答正文提出的同一个疑问，读者不运行代码也能理解关键结论。

章节完稿后做一次**无写作上下文的读者试读**，只提供该章及明确列出的先修：请读者复述章节要解决的问题、解释关键公式中每一项的来源，并完成一个小幅改变条件的变式题。记录答错或无法定位答案的地方，修改后再试。作者或构建工具给出的“覆盖了所有主题”不算通过；必须证明读者能沿正文独立走通。跨章再检查下一章是否调用了本章未教会的能力。

以下情况直接退稿：同一章有两条互不依赖的目标；核心案例中途换对象或假设却未解释；公式只被列出而没有推导或结果解释；练习只复述原例；边界讨论、论文配置或性能账在主问题解决前打断推理。退稿后可以重排、拆章或删去旁支，不以增加篇幅作为默认修复。

## 术语与语言

中文叙述以读者常用的学科说法为准。标准中文数学名词保留中文，例如概率、期望、梯度、矩阵、损失、注意力、反向传播。代码、论文和开发者社区通常直接使用的术语保留英文；首次出现时用一句中文解释其作用，此后固定用同一称呼。不要为了“全中文”创造读者需要反向翻译才能搜索的词，也不要把一句话写成无解释的英文名词串。

| 概念 | 正文默认写法 | 首次出现时说明 |
| --- | --- | --- |
| token、tokenizer | `token`、`tokenizer` | 文本切分后的单位、执行切分与 ID 映射的工具；不要强制写“词元” |
| logits | `logits` | softmax 前的原始分数；不要每次写“未归一化分数” |
| embedding | `embedding` 或“嵌入向量” | 按 ID 查表得到的可训练向量；同页选一种主称呼 |
| one-hot | `one-hot` | 只有目标类别位置为 1 的表示 |
| batch、mini-batch | `batch`、`mini-batch`；叙述可用“一个批次” | 明确样本轴和 batch size；不必处处写“小批量” |
| mask、causal mask | `mask`、`causal mask` | 指明遮住的是注意力候选还是损失位置；避免笼统“遮罩” |
| KV cache、prefill、decode | 保留英文 | 首次说明缓存的 K/V、处理提示阶段、逐步生成阶段 |
| kernel、checkpoint、rank | 保留英文并解释具体语境 | 不用一个中文译名掩盖不同 API 或系统语义 |

某术语若已有自然、稳定且无歧义的中文译名，可以使用中文；关键是全站一致、便于查官方资料和代码。英文首次出现不要求机械添加括号译名。标题和图注也遵守同一规则。更名时检查本站链接、练习、代码注释和相邻章节，避免正文和 API 名称指向不同对象。

## 来源与校验

- 数学定义核对权威教材或原始资料，维基百科可作为定义检索入口与补充链接；不能把它当作推导正确性的唯一依据。库行为以官方 API 文档和可运行代码为准，论文结论核对原文的假设与适用范围。
- 代码须核对正文使用的同一个目标、形状、归约轴与边界条件。运行成功只证明所测断言，不自动证明解释充分。
- MDX 中的 `<details>` 与 `<summary>` 分行书写；`pnpm check` 不能覆盖所有 MDX 解析错误，定稿还要通过站点构建与链接检查。
- 完稿后从读者顺序读一遍，并检查：每节是否推进主问题；首用概念是否已准备好；例子是否连续；术语是否统一；练习是否要求读者迁移；下一章能否只依赖本章实际教过的内容。
- 构建、链接和脚本检查之外，至少用一个新手视角复述“本章为什么引入每个概念”，并用一道变式题检验理解。无法复述或只能照抄例题时继续改稿。

## 逐页交付

一个页面由一个 subagent 独立负责。交付时简述该页原有的断点、遗漏的必要内容、重写后的主线、术语选择与验证结果。主代理检查相邻页面的前后承接，并统一运行站点构建与相关代码验证。导读页也要明确读者路线，但不把它写成术语大全或正文功能说明。
